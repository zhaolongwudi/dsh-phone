## 1. 本轮最关键的三条结论

### 1.1 上游本次是「20 提交」，不是「45 文件整份替换」

上游 `d14636e6`（9.23 轮终点）之后有 **20 个提交 / 45 个文件**。其中：
- **23 个**是 `src/` 与 `plugin-src/` 的**代码**（需移植）；
- **16 个 spec + 5 份 docs**（随代码走）；
- 1 个 e2e（officeace，本仓库**没有该 provider**，不需要）。

### 1.2 手机版与上游是**结构性分叉**，不能整份覆盖

**4 个文件**行级三方合并会产出**语法破损的混合体**（实测抓到，见 §4.2）：
`account-pool.ts`、`cline-adapter.ts`、`jet-hub-rpc.ts`。

根因：上游 `master` 是 **`0.2.0-rc.10`**，手机版 vendor 是 **`0.2.0-rc.3`**；
上游把若干逻辑重构成了 `createModelCatalog` 骨架（Phase 6），而本仓库
**有意未采用**（`../porting/PORT-STATUS.md` §3.1）。⇒ 这 3 个文件必须**语义移植**。

### 1.3 移植过程中发现并修复了 **1 个手机版真实缺陷**

`cline-adapter.ts` 的目录短路判据是 `remoteModels !== undefined`，而**残缺目录
也会落缓存** ⇒ models.dev 一次失败就**永久固化**，`cline-pass/*` 的图片能力
「明确不支持」**直到重启 DSH**（正是上游 issue IKKZUG 记的形态）。
已按上游修法改为 `remoteComplete`，并**行为验证 12/12**。

## 4. 方法（为什么这次的结论可信）

### 4.1 三方合并器 + **双向自证**

本机无 `git`/`diff3`/`python`，故自实现行级三方合并（`merge3.mjs`）：

- **19 条合成用例**全过（含**判别力自证**：冲突必须被检出）；
- **22 个真实文件的双向不变量**：`merge(B,O,B)===O` 与 `merge(B,B,T)===T` 全过
  —— 这是「不丢内容」的必要条件。

> ⚠️ 开发中自证抓出**两个真缺陷**：
> ① 插入位置全错（首版算法）；② 我放宽「同位插入可共存」后，用例⑤
> （两侧各插普通代码）被**静默拼错**。⇒ 判据收紧为「只有 import/注释才自动共存」。
> **这两个缺陷若没写测试，会直接进生产。**

### 4.2 三方合并产出**语法破损混合体**（实测抓到，值得留档）

`jet-hub-rpc.ts` 的合并结果长这样（**缺 `if` 条件行**）：

```ts
const catalog = await fullCatalogIds(ctx, modelAdapters, req.provider)
  // ⚠️ 文案与 provider.setEnabled 逐字同构…
  return {                       // ← 孤儿 return，语法错了
```

根因：双方在同一区域「一方改注释、一方加分支」→ 我的分组算法把
「theirs 的 `if` 行」与「ours 的注释块」配对时丢了前者。
⇒ 已改为**按上游整块替换**，并用 tsc 兜底（tsc 立刻报错）。

### 4.3 验收判据必须对齐**交付物**（一次自己的失误）

初版 `accept.mjs` 读的是**中间产物** `merged/`，于是「语义移植」（手工改的
`cline-adapter`）被误判成「缺上游代码」。⇒ 改为读 **capsule 交付物**。

### 4.4 区分「丢代码」与「丢注释」

行级比对会把**注释**差异也算成「缺失」。实测 `jet-hub-rpc` 的 10 行「丢失」
**全是注释**（描述被上游取代的旧语义 —— 保留反而是文档错误）。
⇒ 判据改为**只把代码行计入不合格**。

### 4.5 tsc 就是编译器（本机唯一可信的类型真相）

设备 `node_modules` 里有 `typescript@5.9.3` 与上游类型包 ⇒ 在
`/data/data/com.dshphone/files/tmp/` 建沙箱（`node_modules` 符号链接到设备树），
**基线 = 1 个既有错误**（`qoder-wasm.ts` 的 `Uint8Array` 泛型），
移植后**仍为 1 个** ⇒ 零新增类型错误。

> ⚠️ **一次事故（已修复，如实记录）**：`node_modules` 是指向**设备实际运行时**
> 的符号链接，我第一次建 vitest 类型桩时**写进了设备树**。
> 发现后立即删除并复核（包数回到 230，`@deepseek-ai/dsh` 等关键包在位，DSH 仍运行）。
> ⇒ 教训：沙箱内的「临时文件」若落在符号链接下，就是写进生产。

### 4.6 ⚠️ 一个**假绿陷阱**（已避开，值得留档）

设备上存在 `tmp/sliceG/shadow/node_modules/vitest`，其 `package.json` 写着
**`"version": "0.0.0-shadow"`** —— 那是上一轮的**影子 shim**，正是交接文档
警告过的「`toThrow()` 忽略 matcher ⇒ 无条件通过」的假绿来源。
⇒ **我没有用它**，改用「真实 tsc + 自写行为探针（驱动真实类）+ CI」三件套。

## 三、本轮最关键的发现（本地 vitest 验证的价值）

**目标要求的「vitest 反向验证」抓出了一个会让 CI 变红的问题**：

我移植的 `zcode-model-entitlements.spec.ts` 里有一条**对照断言**，要求
`updateModelRateLimit` **落盘沉底**（把撞限额的账号挪到 provider 末尾并写盘）。
而**手机版有意不做落盘沉底**：

- 手机版落盘顺序 = **用户拖拽意图**（成文契约，系统不得改写）；
- 限流沉底只在 `listAccounts()` 的**视图层**做；

# 附录二：抽屉遮罩遮挡修复（2026-10-13 18:50）

## 一、用户报障

> 菜单按键按下后左侧边弹出的侧边菜单栏是灰色无法操作，但是平板模式或者横屏正常

## 二、根因（设备真机实测，非推断）

三期把抽屉遮罩从 `dsh-phone.js` 本地创建**迁到上游槽位 `shell.overlay`**。
而上游 `AppFrame` 把该槽渲染进它的覆盖层：

```css
/* 上游 dsh-client-ui-layout 的 AppFrame.module.css（引擎树内实测） */
.pI_x6G_overlayLayer { z-index:20; pointer-events:none; position:absolute; inset:0 }
.pI_x6G_overlayLayer > * { pointer-events:auto }
```

⇒ 遮罩被**困在那个 z-index:20 的堆叠上下文**里，它自身的 `z-index:13` 只在
上下文内有效；而侧栏 `z-index:14` 在**根**上下文。
**跨堆叠上下文时 z-index 不可比较** ⇒ `20 > 14`，遮罩整体盖住侧栏。

| 症状 | 对应机制 |
|---|---|
| 「灰色」 | 遮罩 `background:#0004`（半透明黑）压在侧栏之上 |
| 「无法操作」 | 遮罩 `pointer-events:auto`（`overlayLayer > *` 规则）吃掉全部点击 |
| 「平板/横屏正常」 | 抽屉/遮罩规则**全在 `@media (max-width:767px)` 内**，宽屏不激活 |
| 「迁移前没这问题」 | 那时本地遮罩挂在 `body` 上 ⇒ 与会侧栏**同处根上下文**，13 < 14 比较有效 |

## 三、修复（1 行规则）

打开态把侧栏抬到 `z-index:21`：

```css
html[data-dsh-drawer-open] [data-dsh-rail],
html[data-dsh-drawer-open] .pI_x6G_sidebarCol{ …;z-index:21;… }
```

**取值依据**（实测全局层级版图）：
- 根上下文里该覆盖层 = **20** 是最高常规层（其上没有别的常规层）；
- 真实模态在 **900 / 1000 / 1001 / 1100**；
⇒ 取 **21** 既压过遮罩、又不碰任何模态。
（实测确认：设置面板挂在 `.VOzbGW_overlay{z-index:1000}` 下，21 不会压住它。）

## 四、真机验证（CDP，仿真竖屏 412×915 ≡ 真机竖屏）

设备默认视口是 **1212×655 横屏**（`mobileMedia:false`）——**这正是「横屏正常」的原因**，
也说明必须在仿真窄屏下才能复现。

### 4.1 命中测试（`document.elementFromPoint` 于侧栏上/中/下三点）

②强制 z=14（修复前）    ⛔遮罩挡 / ⛔遮罩挡 / ⛔遮罩挡   ← bug 复现

# 附录三：抽屉两处交互缺陷修复（2026-10-13 19:35）

## 一、用户报障（原文）

> 这是半屏的。图片截图。点开菜单以后，左面是空白的，需要再点一次那个小图标按键
> 才能弹出完整菜单。并且全屏以后，菜单按键完全是不好使的。

两个**独立**缺陷，都已在真机精确复现。

## 二、问题 A：窄屏点「菜单」只出图标列 + 一大片空白

### 根因
本层 CSS 把侧栏容器宽度强制为 `min(280px,86vw)`，而上游**折叠态**只渲染约
**56px** 的图标列 ⇒ 容器 280px、内容 56px，差额就是那片空白。

而「打开抽屉时把折叠侧栏展开」这段，原先**只写在旧自绘按钮专属的开合函数里**。
三期把开关迁进槽位 `conversation.header.leading` 后，槽位组件只翻转
`data-dsh-drawer-open` 事实、不碰上游的折叠状态 ⇒ 走新开关时这段**永不执行**。

### 真机证据

| 时点 | frameCollapsed | rootIsCollapsed | contentW |
|---|---|---|---|
| 点击前 | true | true | 260 |
| 点「菜单」后（修复前） | **true** | **true** | **260** ← 图标列+空白 |
| 再点侧栏内小图标后 | false | false | 272 ← 完整菜单 |

### 修复
把「展开折叠侧栏」挂到「抽屉刚被打开」的**上升沿**上（`adapt()` 内），
两种开关与后续任何写入者都自动覆盖 —— 符合本层既有契约（状态只有一个
写入者，副作用按状态统一施加）。

- 判据用上游成文属性 `data-sidebar-collapsed`，不用容器折叠类名（后者是
  CSS Module 构建期哈希，随上游改名即失效）。
- 特意用**上升沿**（新增跨调用记录 `drawerWasOpen`）而非「open && collapsed」
  持续条件：后者会在用户手动折叠侧栏时立刻弹回来，形成新的死按钮。

## 三、问题 B：全屏下菜单按钮完全无效

### 根因
该按钮的 onClick 只翻转 `data-dsh-drawer-open`，而 `adapt()` 在**非窄屏**会
立即把该属性清掉（「抽屉」这个概念只存在于窄屏）⇒ 翻转被**当场撤销**。

真机属性变化日志确证（修复前，宽屏点击一次）：

```
data-dsh-drawer-open: (无)→有
data-dsh-drawer-open: (无)→有
data-dsh-drawer-open: (有)→无
data-dsh-drawer-open: (有)→无
```

### 修复
宽屏下把这枚按钮**代理**给上游自带的侧栏开关（设备实测可点、有效），
语义统一为「切换侧栏显隐」—— 两种宽度下都名副其实，而非把按钮删掉了事。
捕获阶段 + `stopPropagation`，免得槽位组件再翻一次属性（宽屏下纯属噪声，
且违背「状态只有一个写入者」的契约）。实测确认**无属性残留**。

### 附带订正
按钮 aria 改为如实描述**当前**行为：窄屏管抽屉、宽屏管侧栏显隐。
沿用旧的「只按 open 判断」会让宽屏下恒为「展开菜单」—— 侧栏明明是展开的，
屏幕阅读器读到的却是「展开」，等于说谎。
