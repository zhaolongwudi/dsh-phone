## 4. 内核升级：第一道闸 —— 插件 peer 兼容性

### 4.1 为什么要把它放在第一

第十轮的事故（本轮开头重读并引以为戒）：引擎升 alpha.2 时，`vendor/dsh-providers-hub` 的
`peerDependencies` 仍**精确**钉 alpha.1 ⇒ 引擎的 `evaluatePluginCompatibility`
（`dsh-app-boot/lib/index.js:286`）判不兼容 ⇒ `loadProfileDirectory` **throw**
⇒ **整个 profile bundle 被跳过**，设备上 Jet Hub 整块消失，而**构建/类型检查/单测全绿**。

### 4.2 判据复现 + 全量扫描

写了 `.scratch/engine-a35/peer-scan.mjs`，**逐字复现**引擎判据（`semver.satisfies(rt, range, {includePrerelease:true})`，
只用 `@deepseek-ai/dsh*` 前缀的 peer），semver 取设备树自带那份（7.8.5），**不自实现**。

对 `0.2.1-alpha.5` 扫描 13 个受检包：

| 类别 | 结果 |
|---|---|
| **A 类**（在 `profile.bundles` 里 ⇒ 不兼容会整块消失） | `@deepseek-ai/dsh-web-app` 报不兼容 —— **经查为假阳性**：读的是树里 alpha.3 的包，其 peer 写着 `dsh-shell-env: 0.2.1-alpha.3`；而 **alpha.5 官方包里该 peer 就是 `0.2.1-alpha.5`**（已实测），升级后自然一致 |
| **B 类**（潜伏地雷，不在 bundles、动态 import 不过门禁） | `dsh-channel-qq` 的 peer 精确钉 `0.2.1-alpha.3` ⇒ **已同步为 alpha.5** |
| **兼容放行** | `dsh-our-free-model`（3 条 dsh peer 全兼容）、`@zseven-w/dsh-noema`（7 条）、`dsh-providers-hub`（3 条）、`dsh-providers-hub`（3 条，已是 caret） |

**OFM 为何安全**：它的 peer 用的是 **caret 范围**（`^0.2.0-rc.1`），
`satisfies('0.2.1-alpha.5', '^0.2.0-rc.1', {includePrerelease:true})` = **true**。
这正是第十轮事故沉淀的纪律（「用 `^` 才安全」）生效的体现。

### 6.3 ★ 一处流程教训（留档）

**apply.sh 是「覆盖式铺开」**：它会用 `.github/capsule/overrides/` 覆盖工作区。
我在工作区里重建了 lock 之后又跑 apply.sh，结果 **lock 被工作区那份旧 capsule 里的旧 lock 冲掉**，
导致 `§5.9` 的 lock 断言失败。

⇒ **正确顺序**：先把重建好的 lock 写回 capsule，再铺开/验证。
本轮的最终顺序是：重建 → 拷回 capsule → 同步 capsule 进工作区 → 验证（此时三条硬断言全过）。

### 7.5.2 ★ CI #317 的假红与修正（真实 CI 现场教训）

新门禁推上去后 **CI #317 在步骤 5（apply.sh）失败**：

```
::error::overlay 文件数 41 ≠ 40（有 overlay 静默丢失，Android 适配会缺失）
```

**根因不是 overlay 丢了**，而是我误解了 `apply.sh` 的铺开语义：

- 它是**覆盖式**（`cp -a .github/capsule/overrides/. .`），**只覆盖同名文件、不删除多余文件**；
- 上游 `runtime/overlays/@deepseek-ai` 里留着一份 **`dsh-client-connection/lib/client.js`**
  （capsule 早已改用 `client.browser.js`，而 alpha.5 官方包里也没有 `client.js`）；
- ⇒ 铺开后 = capsule 的 40 + 上游那份残留 = **41**（恒成立）。

**修正**：判据由 `= 40` 改为 **`-ge 40`**（少于 40 才是「我们的 overlay 丢了」），
并按 CI 现场（把那份 `client.js` 放回，凑成 41）复验通过；同时确认仍能抓到真丢失（删两个 → 39 → 红）。

> **两条纪律沉淀**：
> 1. **覆盖式铺开 ≠ 目录同步** —— 任何「文件数 / 集合相等」类的断言都必须先问一句
>    「上游是否可能有我们没管的残留文件？」。判据应从「等于」退到「不少于」，
>    真正的完整性靠**逐个文件的存在性断言**（本段的 `_ovl_check` 里已有 `[ -f ]`）。
> 2. **本地工作区与 CI 的工作树形态不同**：本地是 `clean/` 的复制品（我手工删过那份残留），
>    CI 是纯净上游 clone。**只有 CI 能暴露这个差异** —— 所以门禁改动必须过一次真 CI。
