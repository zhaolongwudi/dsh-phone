## 2. 确认缺陷

### 2.1 高危（2 项）

#### H1 · 聚合层「本轮体积」实为进程级只增峰值 → 小会话死循环 + 学习值失效

**位置**：`overrides/vendor/dsh-providers-hub/src/aggregate-adapter.ts:250`（声明）、`:1444`（筛选消费）、`:1735`（Math.max 写入）、`:1739`（学习消费）。

**根因**：`lastContextTokens` 全仓库**无任何复位点**（grep 证实只有声明/读/`Math.max` 写三处）；
`AggregateAdapter` 经 `registerAggregateLlm` **单实例注册**（:2259），文件内无 sessionId/conversationId
维度隔离（grep 证实零命中）⇒ 它跨请求、跨会话、跨候选累积。字段注释（:243-249）自称
「最近一次观测到的**本轮**上下文规模」，但实现把「单请求内 usage 多帧取最大」外推到了跨请求。

**两个消费点各产生一种回归**：

1. **方案 C 派发前筛选**（:1444-1446）：任一会话/候选一次大 usage（项目文档实测过的 90 万）
   抬高峰值后，**另一个几千 token 的小会话**每次请求都按 `required = 峰值×1.05` 筛候选；
   池内全部候选的已知上限（学习值优先，否则声明值，如 spark-x 262144）都低于它 →
   `kept.length===0 && cooling.length===0` → 主动抛 `CONTEXT_WINDOW_EXCEEDED`（:1486-1490）
   → DSH 压缩链压缩后重发 → **峰值不变** → 再抛 → **压缩重试循环**。
   压缩后的自锁同理：会话已压到 26 万以下，筛选仍用旧峰值，压缩永远解不了锁。
   **后果：小会话/压缩后的会话在进程存活期内永久不可用，重启才恢复**——9.21 要根治的
   「反复截断/反复压缩」家族的新形态，且比被修的那两条更糟。

2. **截断学习喂错值**（:1738-1745）：`finish: max-tokens` 时把 `self.lastContextTokens`（**峰值**）
   而非本次尝试的 `turnTokens`（同作用域 ：1511 声明、:1806 成功自愈路径正在用）喂给
   `rememberContextWindowCeiling`——该函数只在**更小时**覆盖 → 宽候选观测过 90 万后，
   spark-x 真实撞墙 26.2 万时 `rememberContextWindowCeiling(key, 90万)` ⇒ **26.2 万永远学不进去**
   ⇒ 方案 C 的 cap 恒为 90 万 → 恒不跳过窄候选 → 反复 max-tokens 截断。
   这与同文件 :1511-1513 的自警（「与 lastContextTokens 的区别是**关键**的……拿它去放宽窄候选
   就是填大（危险方向）」）和 `context-window-learn.ts:230-232` 的模块级红线**直接矛盾**。
   9.21 的「finish:max-tokens 也算证据」在混合池里**静默失效**。

**亲验记录**：grep 全部读写点 ✓；`registerAdapterIdempotent` 单实例 ✓；无会话维度 ✓；
两处消费点源码逐行核对 ✓（设备树 lib 产物与源码一致）。

**修法方向**：筛选与学习都改用本请求观测（per-request 变量或 `turnTokens`）；
`turnTokens === undefined` 时按「未知不编造」跳过学习（与 ：1511 自警同口径）。

#### H2 · IKLIFH 合条在两类主流程未达成目标 + 无图场景引入 400 形态（探针端到端复现）

**位置**：三处 `flushToolImages` 与消息循环：openai-compat.ts:196-222 + :250 + :262 + :345；
buddy-adapter.ts:344-369 + :426 + :557；lobsterai-adapter.ts:514-540 + :568 + :672。三处状态机
剥注释后逐行同构（机械 diff 证实）。

三个子缺陷：

| # | 触发序列 | 探针实测 wire | 后果 |
|---|---|---|---|
| **F2-A 实时 agentic 流** | 请求以工具结果收尾（0.1.7 常态：模型调完 read_image 等继续生成）→ 历史末尾 flush，`pendingOwnParts` 为 undefined | `user PARTS:[{image_url}]` **纯图无文本独立条** | 按项目自家实测表（图单独一条·无提示句 = ❌「不支持识别图片」），**「工具结果带图模型看不见」的原症状在这条主流程仍在**。合条只在「tool 结果与下一条 user 之间无 assistant」（spec fixture 形态）或「deferred 自身有正文」（legacy 混合）时生效 |

但只断言内容存在（textIndexOf），**未断言形态**；「字符串形态」守卫（:213-221）只测了无
pendingOwnParts 的输入；「中间多一条 user」用例（:142-153）断言 `askIndex > imageIndex`
——**允许分处两条**，恰是 M1 要修的形态（上游提交说明原话：「把 bug 写成了契约」）。

**上游对照**（gitee live）：上游 master 的 `!hasImages` 收窄分支不存在（上游无条件图前置重排，
本仓库收窄是为保普通贴图 `[text,image]` 顺序的有意差异）；**边界 flush 的纯文本 parts 形态
上游同病**（上游 flushToolImages 无收窄分支，ownParts 非空即 push）；F1 的中段搭车子路径是
本仓库修复新开辟的（上游走丢正文路径）。F2 两型两家一致（上游同样不加提示句，
openai-compat.ts:78 的 `TOOL_RESULT_IMAGE_TEXT` 在本文件已是死导出）。

**修法方向**：F1 —— `!hasImages` 且 ownParts 全为 text 时 join 成字符串再 push（保持无图形态
逐字节=旧行为）；F2 —— 末尾/边界 flush 无 own 文本时补回 `TOOL_RESULT_IMAGE_TEXT`
文本部件（上游实测表第 1 行形态 = ✅ 可见）。F2 需产品决策（补提示句 vs 保持纯图），
因为它改变「无后随提问」时的 wire 形态。

### 2.2 中危（4 项）

#### M1 · 三处 `deferred` 判据缺「有挂图/有延后正文」（上游 `32681a8b` 已修 buddy）

**位置**：openai-compat.ts:279 / buddy-adapter.ts:478 / lobsterai-adapter.ts:603，
均为旧形态 `const deferred = toolResults.length > 0`。

**触发**：`tool结果 → 普通user（『好的』）→ 真正提问`。中间条 `toolResults.length===0` →
`deferred=false` → `combined` 因挂图非空 → `flushToolImages(combined)` 把挂图与延后正文、
「好的」一起发出 → 真正提问单独成纯字符串条 ⇒ **图与问重新分处两条，复现 IKLIFH 要消灭的形态**。

**探针实测**（设备树 lib，openai-compat）：wire = `[tool] [图+好的] [提问]`，与上游提交说明
记载的修前 wire 完全一致。

**上游现值**（gitee live 核对）：buddy-adapter.ts:557-559 已修为三条件
（`toolResults.length>0 || pendingToolImages.length>0 || pendingOwnParts!== undefined`）；
**openai-compat.ts:257 与 lobsterai-adapter.ts:589 上游也还是旧形态**——上游只修了 buddy。
本仓库若修应**三处一起**（超出上游），并同步重写 spec:142-153 那条断言（修后三者必须同条）。

#### M2 · workbuddy 渠道发 `reasoning_effort` 吞正文（上游 IKLMIY `8bb10356` 未移植）

上游实测（真实凭据直连 workbuddy.ai，13~15 有效样本/格）：deepseek 系带 `reasoning_effort`
时正文产出率 low=1/14、high=4/15、max=6/13；**不发该字段 15/15**。唯一变量是字段在不在。

本仓库：`registerBuddyLlm` 双产品共用（index.ts:627 codebuddy / :682 workbuddy），
buddy-adapter.ts:1802/:1808 **无条件发** `reasoning_effort`，无 product 区分 ⇒ workbuddy 中招
（连续 23 步零正文的真实报障形态）。上游修法「该渠道一律不发」；本仓库落点即
`this.product.id === 'workbuddy'` 时跳过（product.id 在 provider-registry.ts:188 可判别）。

#### M3 · 登录轮询三处时序/生命周期缺陷（双源：主审独立发现 + 子代理深读相互印证）

1. **成功分支 `stopPoll()` 滞后于两个 await**（jet-hub.js:3166-3171）：失败分支（:3148）与
   超时分支（:3107）都已把 stopPoll 前置（:3134-3147 有专门守卫注释「必须最先」），
   **唯独成功分支** `await loadAccounts(); await loadCredits(); stopPoll();`。
   三型后果：a) done:true 落在 deadline 前 1~3 秒且刷新 ≥1 tick → 下一 tick 命中超时分支 →
   **账号实际已添加，UI 永远停在红色「登录超时」**（:3114 的「若账号其实已经添加」兜底文案
   恰是该假超时的自供）；b) 失败终态与超时分支并发 → IKLI7J 打通的真实失败原因可被泛化
   超时文案覆盖；c) 不撞边界时 await 期间每秒有 tick 重复进入成功分支 → loadCredits（逐账号
   上游请求）放大 2~3 轮，可能触发限流。
2. **`setVersion` 重挂载静默杀轮询**（key 机制 :6265 `key: p.id + '-' + version`；触发点
   :5922 供应商开关后 / :6069 一键签到完成后 / :6192 备份导入后）：登录等待 5 分钟内点
   「一键签到」（耗时数十秒~数分钟，与等待高度重叠）→ ProviderPanel 整个卸载 → 清理函数
   （:2644-2655）掐轮询并 **close 授权窗口**，零提示 → 后台流程收不到回调，failLogin 写了
   终态表但没有客户端在轮询 → 失败原因永不可见。切面板（:5879）属用户显式离开可算接受。
3. **`login.submitSms` 记账失败误报**（jet-hub-rpc.ts:3230-3256）：验证码正确、凭据已落库、
   仅 `pool.updateAccount` 抛错也被 catch 统一返回 `{done:false, error}`（可重试形态）——
   msgid 已消费，重试必败；且此路径**不写终态表**。主扫码路径同场景走 `failLogin`
   （:1973-1996）有 `loginCredentialLanded` 判据按成功处理——**同文件两套同义判据**。

#### M4 · minimax `input_json_delta` 绕过空名防线（探针验证下游链）

**位置**：minimax-messages.ts:663-694。丢弃闸门只挡 `droppedToolIndexes.has(index)`；
当 `state === undefined`（上游只发 delta 不发 content_block_start，或 block-start 是未知 type
被忽略）且 index 不在丢弃集时，yield **无条件执行**：`id: CallId('')`、无 name 键、带
argumentsDelta。

**下游链已核实**（设备树 lib）：网关 `openai-gateway/stream.js` 的 `consumeChunk` 按 index

`outputItemJson` 输出 `call_id:''` / `name:''` → 宿主 BlockAssembler 组装空名块持久化 ——
正是 PR#93 要堵的 `unknown tool ""` → 会话报废家族路径。触发依赖畸形上游
（与本文件自设威胁模型一致：注释明确引用 qoder 无名帧），正常流不可达。

**修法一行**：`if (state === undefined || state.type !== 'tool-call') return`。
