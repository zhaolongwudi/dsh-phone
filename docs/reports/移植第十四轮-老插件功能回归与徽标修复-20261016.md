## 1. 缺陷 ①：徽标恒占位（根因与取证）

### 症状

输入框模型选择器左侧那枚胶囊恒显示占位 **「聚合 · 待首次请求」**（`<span>`，点不开）。

### 根因：**存与取的键不一致**

| 侧 | 键 | 位置 |
|---|---|---|
| 写（服务端） | **路由键** `aggregate` | `aggregate-adapter.ts`：`activeRoutes.record(AGGREGATE_PROVIDER, …)` |
| 读（客户端） | **模型键** `glm-5-3` / `auto` | `usage-badge.js`：`readActiveProvider(modelId)`，`modelId = state.current.model` |

`ActiveRouteRegistry` 是 `Map<routerProvider, …>`，按模型键查**必然 miss** ⇒ 端点恒回
`{provider: null}` ⇒ 徽标恒占位。

### 真机取证（`hub-rpc.mjs`，运行中实例）

```
router.activeRoute {"provider":"aggregate"}            → loomy      ← 有值
router.activeRoute {"provider":"glm-5-3"}              → null  ❌
router.activeRoute {"provider":"deepseek-v4-1-flash"}  → null  ❌
```

### 修法（最小改动）

`record()` 增加第 4 个可选形参 `modelKey`，**同一时刻两处都写**；聚合适配器传入
它**本来就有的** `modelKey`（`dispatch(targets, options, modelKey)` 的第 3 形参，零额外取数）。

⚠️ **只有聚合传 `modelKey`**：客户端传的是**裸**模型 id，而 `aggregate/auto` 与
`jet-hub-auto/auto` **同名**；若自动适配器也写模型键，它会覆盖聚合同名键、徽标显示成
旧 auto 的渠道。徽标只在选中 `aggregate` 时才发这个查询（`isAggregate` 门控），
故旧 auto 不写反而**消除**了串扰。

### 单元验证（从构建产物里抽出真实类跑）

```
只写路由键（等价修复前）: read(aggregate)=有值   read(glm-5-3)=null
带 modelKey（修复后）    : read(aggregate)=有值   read(glm-5-3)=有值
```

⚠️ **宿主侧需重启 DSH 才生效**（`pack.js` 是进程内动态 import，进程已缓存）。
客户端侧（补丁 G）**刷新页面即生效**（见 §5 的实测判据）。

## 2.5 缺陷 ③：聚合面板的开关对「非临期」候选是死的（本轮新发现）

### 症状

聚合面板里，**未接入临期折算**的渠道（qoder / cline / gemini / opencode / raccoon /
minimax / qodercn）的候选，开关**点了没反应**；且它们被显示成**「已拒绝」**——
而用户从没点过。

### 根因：宿主下发两个字段，客户端只读了一个

| 字段 | 含义 |
|---|---|
| `state` | `'allowed'` / `'rejected'` / `'default-rejected'` —— **三态门控** |
| `rejected` | `state !== 'allowed'`，语义是「**当前不参与轮换**」（`aggregate-adapter.ts:590`） |

npm 版客户端（`dsh-providers-hub@1.6.261016`）**从不读 `state`**（全文 0 处）：

1. `rejectionsFromCatalog()` 按 `rejected === true` 摊平 ⇒ 把「默认不参与」也摊进拒绝表
   ⇒ 面板显示**「已拒绝」**（撒谎）；
2. 点开关一律发 `aggregate.setRejected { rejected: false }` ⇒ 对这类候选
   **删的是一个根本不存在的键** ⇒ 宿主状态纹丝不动。

### 受控实验（本机实测，可复跑）

以 `glm-5-3-flash` 的 `qoder/gfmodel`（`expiryWired:false`）为例：

```
【1】基线                               state=default-rejected  rejected=true
【2】setRejected {rejected:false} → ok  state=default-rejected  ❌ 没变（死开关）
【3】setAllowed  {allowed:true}   → ok  state=allowed           ✅ 这才是「手工打开」
【4】setAllowed  {allowed:false}  → ok  state=default-rejected  （回滚，状态已复原）
```

全库分布：**145 条 `allowed` / 38 条 `default-rejected`** ⇒ 38 条候选的开关是死的。

### 修法：照抄上游的权威实现，不自己发明

gitee 上游 `plugin-src/client/aggregate-panel-logic.js` 已有正确实现
（`candidateToggleAction` / `candidateStateOf` / `rejectionsFromCatalog`），其注释
明确记录了这个缺陷的两次修订（2026-10-15 加 `state`、老宿主回退）。补丁 H 把语义
逐条搬进 OFM 的 `client.js`：

- **摊平拒绝表**：只有 `state === 'rejected'` 才算用户显式拒绝；
  **老宿主（响应无 `state`）回退到只看 `rejected`**（否则升级期用户存过的拒绝全丢）。
- **点哪张表**由 `state` 决定：`rejected` → 删拒绝；`allowed` → 未接入写白名单 `false`、
  已接入写拒绝；`default-rejected`（及**未知/畸形值**）→ **写白名单 `true`**（手工打开）。
  ⚠️ 未知值**不得**走 `allowed` 分支 —— 那会发 `allowed:false`，把「读不懂的状态」
  写成用户明确不允许（上游注释专门记了这条）。
- **文案说真话**：`已拒绝` / `参与轮换` / **`默认不参与`**（三态各不相同）。

### 验证（11 项单测 + 真数据分派 + 端到端 + **真渲染**）

```
单测（纯函数，含老宿主回退）        11/11 通过
真实 catalog 逐条分派：
   145 allowed          → setRejected
    38 default-rejected → setAllowed   ← 修复前这 38 条发的是 setRejected（无效）
摊平结果：拒绝表 0 条（修复前会把 38 条默认不参与误标成「已拒绝」）
端到端：模拟补丁后客户端点击 → default-rejected → allowed ✓（随后已回滚）
真渲染：AggregatePanel（92 模型 / 27605 字符）渲染出
        「qoder · gfmodel · x0.1  **默认不参与**」✓
反向：对**未打 H** 的旧文件跑同一断言 ⇒ 同一行渲染成「**参与轮换**」（假话）⇒ 断言变红 ✓
```

### ⚠️ 验证器本身的三次返工（都是我的缺陷，如实记录）

`render-aggregate.mjs` 是新写的（因为 `render-check.mjs` **根本渲染不到这个面板**）：

1. **`renderToString` 不跑 `useEffect`** ⇒ `models` 恒 `null` ⇒ 面板只渲染
   「读取中…」那半张壳（844 字符），`renderCandidate` **一次都不跑** ——
   而那正是补丁 H 改的地方。⇒ 必须注入 `useState` 初值。
2. **shim 的计数器写在 Proxy 的 `get` 里** ⇒ 每次读 `useState` 都新建一个
   「第一次」闭包 ⇒ 所有 state 都拿到目录数组 ⇒ 输出仍 844 字符、
   **与不注入时逐字相同**（等于 shim 没生效）。⇒ 计数器必须 hoist 出去。
3. **序号数错**：`expanded` 是第 **5** 个 `useState`（models/rejections/busy/
   **notice**/expanded/…），我按第 4 个注入 ⇒ 把 `{modelKey:true}` 塞给了 `notice`
   ⇒ 抛 `Objects are not valid as a React child`。⇒ 序号必须回源码数。

> 这三次都不是产品缺陷，而是**验证手段不可信** —— 与仓库既有记录同型。
> 故最终判据落在「**同一断言对已修/未修两份文件给出相反结果**」上（见上方「反向」一行）：
> 只有能区分，才算验证。

## 3. 两个真实踩坑（都导致过「补丁完全无效」）

### ① 抽取起点切错 ⇒ IIFE 返回空对象

老产物是 esbuild 的 CJS 包装：

```js
var module = { exports: {} };
var exports = module.exports;
var client_exports = {};
__export(client_exports, { apply: () => apply, … });
module.exports = __toCommonJS(client_exports);   ← 真正的导出在这里
```

从 `var exports` 开始切（丢掉 `var module`）：那行会去**外层**找 `module` ——
即 OFM 包装器的 `module`，把老 bundle 的 `exports` 接到 OFM 的导出上，
**反过来劫持 OFM 自己的 `exports.apply`/`exports.name`**。

- 实测症状：无头校验里**注册槽位从 4 个掉成 1 个**（只剩 jet-hub，OFM 三枚全没）。
- 修法：**从 `var module` 开始切**（自带 `module` 声明，且把导出接线整段包含进来）。
- 加固：加断言「`module.exports = __toCommonJS(client_exports)` 必须在场」+
  「`function apply(ctx)` 恰好 1 个」。

### ② 验证器自己的 `slots.register` 是丢弃桩 ⇒ 误判

两个 bundle 都写成 `ctx.slots.inject(名, () => ctx.slots.register(定义, 组件))` ——
真正被调用的是 **`ctx.slots.register`（外层那个）**，不是 inject 回调收到的
`register` 形参。初版把它写成 `() => () => {}`，于是**一个槽位都抓不到**，
被误读成「补丁 G 没生效」。

> ⚠️ 教训与仓库既有记录同型：**验证手段本身不可信**时，会得出与事实相反的结论。
> 故本轮每个验证器都先对**已知可用的基线**跑一遍（见 §4）。

### 6.2 为什么本轮**不做**它（决策依据，不是偷懒）

1. **三个端点是一组，拆开做会更糟**：`setOrderMode`（切到「按手工」）与
   `rejectNonExpiring`（一键恢复）各只是一个按钮，但 `setOrder` 需要**整套 HTML5 拖动**
   （onDragStart/onDragOver/onDrop/dataTransfer + 落点计算 + 松手提交）。
   只做前两个 ⇒ 用户能切到「按手工」却**拖不动** ⇒ **半个功能比没有更误导**。
2. **它不挡核心价值**：宿主的 `orderMode` **缺省就是 `expiry`**（实测 `"expiry"`），
   「临期优先 / 同模型换供应商」由**宿主**排序，**本就不依赖这个面板**
   —— 951 次请求分到 officeace 523 + loomy 387、错误率 0.67%，正是它工作的证据。
   缺的只是**手工覆盖**（可选精调）。
3. **它要改的正是本轮刚修好的那段**：补丁 H 已改 `renderCandidate` / `onToggleRejected`，
   而排序版面板要**整块替换** AggregatePanel。在长会话尾部做「刚修完又整块换掉」，
   返工与踩锚点的风险最高。⇒ 应作**独立一轮**：先替换面板，再在其上重放 H 的语义
   （H 的 4 个纯函数与上游 `agg-logic.js` **语义一致**，已逐条比对，可作合并基线）。
4. **它的验收面是「交互」—— 而这一点本轮只解决了一半（原判断已修正）**。

   ⚠️ **先纠正我自己**：本轮最初写的理由是「没有可用的交互验证手段」——
   那是**错的**。本轮末尾建了 `check-aggregate-wiring.mjs`，它**真的调 `onClick`**
   并断言发出去的 RPC（并已验证有区分力：对未打 H 的文件正确失败）。
   ⇒ **「点得对」现在验得了**（至少对按钮类交互）。

   仍然**验不了**的是：**HTML5 拖拽**（`onDragStart` → `onDragOver` → `onDrop` →
   `dataTransfer`），因为它需要真实 DOM 事件与 `DataTransfer` 对象，
   而设备上**没有 jsdom / happy-dom / linkedom**（已逐一查过）。
   而本仓库**真的栽过这个跟头**，CSS 注释逐字记着：
   > 拖动本身在此前是**坏的**（`onDragStart` 漏了 `dataTransfer.setData`
   > ⇒ 浏览器不触发拖拽），所以那时只有箭头能用 —— 修好拖动后才删箭头。

   **⚠️ 不过这里我又修正了自己一次**：拖拽**并非完全验不了** ——
   可以像 `check-aggregate-wiring.mjs` 那样取出元素树，**传桩 event** 直接调
   `onDragStart({ dataTransfer: { setData: spy } })`，断言 `setData` **确实被调用**，
   那正好钉住上面那个历史 bug。
   真正验不了的只是「落点算得对不对、松手提交对不对」那类**几何 + 时序**行为
   （需真实布局）。

   ⇒ 结论：**排序功能是一个整体**（切模式 + 拖动 + 一键恢复）。下一轮可以：
   ①「切模式」「一键恢复」两个按钮 —— 用 `check-aggregate-wiring.mjs` 直接验；
   ② 拖动 —— 验到「`setData` 被调用」这一层；
   ③ 落点/提交 —— **仍需真机点一下**。
   因为 ③ 恰好落在本仓库历史上坏过的那处，**故仍建议与真机验收同一轮落地**。

⚠️ **注意事项（留给下一轮）**

  需确认页面隐藏时的行为（上游注释称「标签页在后台时跳过」）。

  `.dim-jh-aggDragOver` / `.dim-jh-aggOrderActions` / `.dim-jh-aggInactiveSection` …）

### 6.3 「短信登录 / 验证码」—— 结论已修正：**功能本来就在，只是不走那两个 RPC**

**最初（本轮中途）的判断是错的**，我按端点名推断「短信登录没有界面」。实测推翻了它：

**① 服务端有完整的「本地登录页」实现**（不是靠客户端调 `login.sendSms`）：

| 文件 | 作用 |
|---|---|
| `loomy-wechat-login.ts` | 本地弹窗页（`/wechat/qr`）：**内联二维码 + 首次绑手机号表单** |
| `loomy-auth.ts:177` | `sendSmsCode()` —— 由**服务端**在登录页里调用 |
| `raccoon-login-page.ts` / `zcode-carrier-page.ts` | 同型的其他「本地登录页」 |

**② 实测 `account.create` 返回的就是登录页 URL**：

```console
$ node hub-rpc.mjs account.create '{"provider":"loomy"}'
{ "ok": true, "value": {
    "accountId": "loomy-c1fba771",
    "loginUrl": "http://127.0.0.1:42277/wechat/qr"   ← 二维码 + 绑手机号表单都在这一页里
} }
```

客户端只需照常 `window.open(loginUrl)` —— 与 codearts / lobsterai / qoder / trae / cline
**完全同一条路径**。

**③ gitee 上游的注释还记着这个设计变更的原因**（原文）：

> **真实缺陷**（用户报障「新建账号失败：Loomy 短信登录需要手机号」）：
> 早期这里为 Loomy 分出一个「短信表单」分支，而表单要等 `account.create` 返回才渲染、
> `account.create` 又要求先有手机号 —— **顺序死锁**，表单永远出不来。
> 改用微信扫码后该分支已删除。

⇒ 结论：**「短信登录」不是丢失的功能，也不是待开发的新功能 ——
它已被上游改成「登录页内完成」并正常工作**。`login.sendSms` / `submitSms` 两个端点是
**为该登录页准备的内部接口**（由服务端在页面里调用），客户端本来就不该直接调。
⚠️ **此结论为实测所得**（`account.create` 返回 `loginUrl`）；本轮实验创建的账号已删除，
Loomy 账号数回到 3。
