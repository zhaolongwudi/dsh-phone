## 1. 开工须知（新会话必读）

### 1.1 构建链与产物关系

```
仓库 main（上游纯镜像，永不修改）
   ↓ 构建时 apply.sh 铺开
capsule/files/.      → 复制到工作区（全新增路径，不覆盖上游）
capsule/overrides/.  → 覆盖到工作区（上游同名文件 + 胶囊接线）
   ↓
rebuild-vendor.sh：pnpm install → vitest(27 spec) → pnpm build:all（tsc + esbuild）
   ↓
build-apk.yml：python3 scripts/build-assets.py → gradlew assembleDebug → gh release
```

**关键**：`apply.sh` 的自检段（:79-327）用大量 `grep -qE` 锚定「接线点形态」——**改实现时必须同步改自检，否则构建直接中断**（作者已实测踩过）。这是有意的防"静默失效"设计，不是可以绕过的障碍。

### 1.2 ⚠️ 工具纪律：本机 `grep` 是 toybox，不支持交替模式

**这是本轮最贵的教训，直接导致过一次误判。**

```sh
grep --version   # → toybox 0.8.12-android (is not GNU grep 9.0)
grep -rl "A\|B" .      # → 静默返回空结果（不报错！）
grep -rl -e A -e B .   # → 正确
```

**规则**：
1. 一律优先用内置 grep 工具（ripgrep）；
2. 必须用 shell 时，**只用 `-e` 分开写**，绝不用 `\|`、`\b`、`\s`；
3. **任何"检索未命中"的结论都必须用第二种方式复核后才能写进报告**。

本轮即因此撤销了一条误判（见 §3.4）。

### 1.3 探针范式（修复后如何验证）

设备树是**当前装机版本**（含已发布的补丁），可直接 `require` 其 lib 产物跑行为探针。这是本项目最有力的验证手段，修复后应立即用它回归：

```sh
export PATH=/data/data/com.dshphone/files/bin:$PATH
LIB=/data/data/com.dshphone/files/tree/node_modules/dsh-codearts-auth/lib
```

常用探针模板见 §7.3。**注意**：设备树产物要在重新构建安装后才更新，改源码后需重跑 `rebuild-vendor.sh` 并确认 `lib/` mtime 变化。

### 1.4 修复纪律（沿用项目既有约定）

- **外科手术式修改**：不顺手改相邻代码；每行改动可追溯到某条缺陷。
- **改了必须反向验证**：临时把修复回退，确认对应用例/探针**变红**；否则可能是同义反复。
- **改 `lib/` 需重启 DSH 才生效**（宿主侧不热重载，只有 client bundle 有 HMR）。
- **上游大改被覆盖文件时 tsc/测试会显式失败**——不会静默丢功能；需对照新版上游重新生成 override。

**F-01｜对外分发的 APK 是 debug 构建（安全 + 供应链）**
- **位置**：`CAPSULE/build-apk.yml:158`（`:app:assembleDebug`）、`:168`（`gh release upload … app/build/outputs/apk/debug/app-debug.apk`）、`update-readme.py:23`（把该 URL 写进 README 下载区）、`MainActivity.kt`（全文无 `setWebContentsDebuggingEnabled(false)`）
- **触发**：任何用户从 README 下载安装

- **修法方向**：改 `assembleRelease`（需补 signingConfig）；或至少补 `WebView.setWebContentsDebuggingEnabled(false)` 并评估 debuggable 的影响面
- **验证**：`aapt dump badging app-release.apk | grep debuggable`；或 `adb shell run-as <pkg> ls` 应失败
- **来源**：平行深读（Android/构建组）+ 我验收

**F-02｜破坏性操作的确认按钮文案错位（移动端专属）**
