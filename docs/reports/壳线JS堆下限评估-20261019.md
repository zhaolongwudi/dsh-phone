# 壳线候选立项评估 · JS 堆自适应下限（2026-10-19）

> **背景**：本轮上游检查发现 kelai141/dsh-mobile-apk 从 v0.14.6 走到 v0.14.8，其第 1 项修复
> 「小内存设备上引擎起不来（JavaScript 堆太小）」与我们的壳同构（我们同样没设堆参数）。
> 本文是**只读评估**：不改任何代码，判据全部现场实测。
>
> **结论一句话**：缺陷的**机理**在我们壳上真实存在，但**照搬它的修复会让我们这台设备实亏** ——
> 实测本机 V8 自动推导上限 **2144 MB**，而它的 `clamp(总内存/2, 512, 1024)` 会把我们压到
> **1120 MB（-48%）**；且本机历史日志**零堆耗尽事故**。⇒ **不建议现在改**；若要防御，
> 只做「下限兜底」而不是全局钉一个上限。

---

## 1. 我们壳的现状（三条独立判据）

### 1.1 代码面：启动路径只有一处，且确实没有堆参数

上游启动器 `app/src/main/java/com/dshphone/NodeRunner.kt`（jwoo `7f55f00c`，346 行）里唯一
起引擎的地方是 `start(ctx)`：

```kotlin
val cmd = listOf(
    node.absolutePath,
    "--expose-internals",       // hmr/内部 loader 需要
    "--no-warnings",
    bin.absolutePath,
    "--profile", "phone", "--port", "3080",
    "--no-open",
)
val pb = ProcessBuilder(cmd)
pb.environment().putAll(prepareEnvironment(ctx))   // 见 1.2
```

`prepareEnvironment()` 返回的 14 个键（`DSH_PHONE_*` / `LD_LIBRARY_PATH` / `HOME` / `DSH_HOME` /
`TMPDIR` / `OPENSSL_CONF` / `PATH`）中**没有** `NODE_OPTIONS`。

### 1.2 运行面：进程参数与环境的实测

```
$ tr '\0' ' ' < /proc/4860/cmdline
.../lib/arm64/libnode.so --expose-internals --no-warnings .../dsh/lib/bin.js --profile phone --port 3080 --no-open
$ tr '\0' '\n' < /proc/4860/environ | grep -i 'NODE_OPTIONS\|MAX_OLD'
（无 NODE_OPTIONS / 无堆变量）
```

⇒ 与 kelai 描述的「启动参数没有堆标志、运行环境没有 `NODE_OPTIONS`、profile 也没有」**逐条吻合**。

### 1.3 数量面：我们比它少一处注入点

它有**两处**注入点（壳侧 `NODE_OPTIONS` + 快照内启动器）。我们的引擎只由 Kotlin `ProcessBuilder`
拉起（`NodeRunner.start`），**没有**「快照内启动器」这个第二处 ⇒ 真要改，落点是**一处**，
改动面比它小。

## 2. 关键实测：本机 V8 推出的上限，以及它的 clamp 会怎么改我们

命令（`/data/data/com.dshphone/files/bin/node` 即 `libnode.so` 的符号链接）：

| 情形 | `heap_size_limit` 实测 |
|---|---|
| **本机自动推导**（`MemTotal` = 11,524 MB） | **2144 MB** |
| 显式 `--max-old-space-size=1024` | **1120 MB** |
| 显式 `--max-old-space-size=512` | **608 MB** |

⚠️ 后两行同时印证了 kelai 那条「设 `--max-old-space-size=N` 的实测结果是 **N+96 MB**」的判据
（1024+96=1120 ✓、512+96=608 ✓）—— **它的测量方法可信**，这不代表它的取值对我们合适。

**它的修复取值**：`clamp(总内存 / 2, 512, 1024)` MB。对本机（总内存 11.5 GB）⇒ `clamp(5762, 512, 1024)`
= **1024** ⇒ 实际堆上限 **1120 MB**，即把本机现在的 **2144 MB 砍掉 48%**。

**这是一处必须说清的反向风险**：kelai 的动机是「兜住小内存机型起不来」，做法却是给**所有**机型
钉一个上限；对我们这种大内存设备，代价是**大上下文 / 长任务更早 OOM**。

|---|---|---|

## 4. 判定

| 问题 | 判定 | 依据 |
|---|---|---|
| 缺陷机理存在吗 | **存在** | §1 三条判据（代码 / 进程 / 与上游描述逐条吻合） |
| 我们这台设备受害吗 | **否** | 2144 MB 上限、运行正常、零事故 |
| 该照搬它的修复吗 | **不应该** | 会把本机上限砍到 1120 MB（-48%），收益为 0、风险为正 |
| 该做点什么吗 | **可以，但只做下限** | 见 §5 |

**为什么"只做下限"才对**：真正的失效形态是「V8 按整机内存推出**过大**的值，超过 Android 给本 App
的实际可用内存 ⇒ 启动即被 LMK 杀」。要防它，正确做法是**只在推导值不合理时才介入**，而不是给
所有设备钉同一个数：

```kotlin
// 伪代码：仅当 V8 推导值偏低时抬到下限；推导值高时不干预（保持现状）
// 判据来源：本机实测 heap_size_limit = min(…)，且 N+96 规律已复现
val floorMb = 512
// 仅在确认推导值 < floorMb 时注入 --max-old-space-size=floorMb
```

⚠️ 更稳的形态是「读完 `/proc/meminfo` 只算**下限**、上限交给 V8」，但**具体阈值现在没有数据支撑**
（我们只有一台设备的一次实测），**不该在这个阶段拍数字**。

## 5. 若将来要落地：改动面与风险（本次**未执行**）

| 项 | 内容 |
|---|---|
| 落点 | `NodeRunner.kt`（**上游文件**）。capsule 中**没有**它的整份覆盖（`overrides/app/` 只有 4 个文件：`dsh-phone.js`、`dsh-phone.css`、`MainActivity.kt`、`AndroidManifest.xml`） |
| 施加方式 | 按 apply.sh §2.8 既有模式做**就地精确替换 + 落点断言**（锚点是 `"--no-open",` 那段 cmd 或 `prepareEnvironment` 的返回值），**不要**往 overrides 丢整份文件（会遮蔽上游后续修复） |
| 可编译性 | ⛔ 本机**无 java / gradle / kotlinc** ⇒ Kotlin 改动的唯一验证通道是 **CI 真编译**；本地只能做文本级自检 |
| 回归风险 | 阈值定错会**降低**引擎可用堆（§2 已量化：照抄 = -48%）；且堆耗尽的表现是**进程被杀**，排障成本高 |
| 判据要求 | 改前须先有「本机推导值 + 至少一台小内存设备的实际值」，否则是拿主设备当小白鼠 |

## 6. 建议

1. **本轮不动**（保持现状）。本机数据不支持这次改动，且它自己的修复未获真机验证。
2. **登记为一个"条件触发"待办**：触发条件是「引擎出现启动失败 / 堆耗尽（`dsh-console.log` 出现
   `Reached heap limit` 或 `boot-fail`）」，或「换用小内存设备」。届时按 §5 落地，并**只加下限**。
3. **先补一个低成本的观测面**（可选，且与它 0.14.8 的做法同构）：在 `NodeRunner` 启动日志里记一行
   `engineHeapMb=`（读 `/proc/meminfo` + V8 实际值），这样下次真出问题时**有第一手现场** ——
   这正是它那条 Release 里承认缺失的东西。
