## 1. 问题①：opencode 模型列表读不出

### 证据

```
model.list {provider:'opencode'} → no adapter registered for provider "opencode"
model.list {provider:'aggregate'} → ok（模型齐全）
model.list {provider:'officeace'} → ok
```

### 根因链

1. OFM 挂载渠道包时传 `disableOpencode: true`（`dsh-our-free-model/index.js` 第 1033 行：
   `pack.apply(scoped, { disableOpencode: true, outlet: … })`）；
2. 该开关由 `patch-channelpack-port.mjs` 的 `opencode-open` / `opencode-close` 两处适配实现
   —— 上游那条 OpenCode 接入（含匿名通道）**整段不注册**；理由是 OFM 自带匿名免费车道，
   两者并存会重复接入（历史上抢端口 / 争 `.credentials.yaml`）；
3. 但 `provider-registry.ts` 里 opencode 仍是 `channel: true`（可视渠道）；
4. 老 Jet Hub 页（补丁 G 注入）与 OFM 渠道页（补丁 D）**都按这份 registry 渲染卡片**，
   且都调同一个宿主 RPC `model.list` ⇒ **两处界面必然都失败**（同一根因，不是两个 bug）。

### 修复（只改显示名与卡片说明）

三处形态各自需要处理（实测 `client.js` 里 `OpenCode` 共 3 种、5 处）：

| 形态 | 位置 | 由谁改 |
|---|---|---|
| `label: "OpenCode",` ×2 | `client.js` 内嵌 registry 副本（OFM + 注入的老 Jet Hub） | 新脚本 `patch-opencode-note.mjs` |
| `displayName: "OpenCode",` ×2 | 同上 | 同上 |
| 渠道卡片行的 `note` ×1 | 补丁 D 生成的卡片（`CHANNEL_META`） | `patch-phone-port.mjs` 的 `CHANNEL_META.opencode.note` |
| （宿主侧）`label` / `displayName` 单引号 ×1+1 | 渠道包 `provider-registry.ts` | `patch-channelpack-port.mjs` 新增适配 |

**刻意不动** `channel` / `credits` / `rateLimit` / `accountTest` —— registry 注释记着
「早期把 `credits.balance` 登记为 `false` 曾把整个徽标挡死」。

### 验证

```
pack.js 含「免费车道接管」        = 1 处（registry 标注）
client.js label 标注              = 2 处
client.js displayName 标注        = 2 处
client.js 卡片 note 标注          = 1 处
```

## 2. 问题②：一次请求两条日志（以及③统计翻倍）

### 证据（账本逐条明细，铁证）

```
 1) aggregate  deepseek-v4-1-flash   in=1919 out=1901 cache=334592
 2) officeace  deepseek-v4.1-flash   in=1919 out=1901 cache=334592
 3) aggregate  …                      （与第 4 条成对，数字同样逐字节相同）
```

`usage.tokenLedger` 的聚合视图也一致：`aggregate` 与 `officeace` 两个 provider 的
`requests / inputTokens / outputTokens / cacheReadTokens / totalTokens` **完全相同**
（各 11 次、140775 / 8489 / 3350784 / 3500048）。

### 根因

Token 记账包装 `wrapAdapterWithTokenLedger` 挂在 `registerAdapterIdempotent` 里，**对每一个
适配器统一包装**（`llm-register-compat.ts`）。用户使用**聚合模型**时：
聚合适配器（`aggregate`）转发 → 真实渠道适配器（`officeace`）**也被包了一层**
⇒ 一次用户请求落账**两次**。两条没被去重，是因为两层的 wire 模型名不同
（`deepseek-v4-1-flash` vs `deepseek-v4.1-flash`）。

**触发条件**：仅在使用「聚合」模型时双份；直接选某个渠道的模型只记一条。
**不是本次同步引入**：新旧 pack.js 都含同样的包装逻辑（已比对 03:28 之前的备份）。

### 修复（宿主侧，治本）

在 `patch-channelpack-port.mjs` 新增 `UPSTREAM_EDITS` 机制（对上游自带文件的幂等适配），
第一条即：

```js
function wrapAdapterWithTokenLedger(providers, adapter) {
  if (providers[0] === "aggregate") return adapter;   // 聚合层不记账
  const provider = providers[0] ?? "";
```

一处修好**全部消费者**：运行日志、数据看板、`usage.tokenLedger`、`usage.tokenLedgerHistory`
（落盘日聚合同样按 provider 分桶累加，双份会翻倍）。

### 验证（产物里实测到的真实代码）

```js
function wrapAdapterWithTokenLedger(providers, adapter) {
  if (providers[0] === "aggregate") return adapter;
  const provider = providers[0] ?? "";
```

（`pack.js` 是 esbuild 产物、**注释被剥离**，所以按注释标记查找会得 0 —— 判据要用**功能形态**。）

## 3. 问题④：胶囊 Token 用量 vs 数据看板

### 先定位「胶囊」到底是哪个

实测运行页面（`http://127.0.0.1:3080`）输入框下方是四段读数：

```
OfficeAce • 15204.51积分        5 轮 765 步·147 tok/s
245M tok·缓存命中 79%           21%
```

- `OfficeAce • 15204.51积分` = **用量徽标**（`usage-badge.js`），数据源 `usage.badge`
  → 那是**账号配额/余额**读数（`remaining / total`，单位 token 或积分），**不是本机消耗**；
- `245M tok·缓存命中 79%` = **上游会话统计**（`@deepseek-ai/dsh-client-ui-chat`）。

### 两者的口径与范围

| | 胶囊（会话统计） | 数据看板 |
|---|---|---|
| 数据源 | 适配器发射的 `usage` 帧（`zcode-anthropic.ts` 注释明说「UI 的 tps / token 用量 / 缓存命中 / 上下文占用全靠它」） | 渠道包账本（`recordThroughStream` 捕获**同一批** usage 帧） |
| 总量口径 | 上游 `usage.totalTokens` | `inputTokens + cacheReadTokens + outputTokens`（同口径） |
| 缓存命中率 | `cacheReadTokens / (totalTokens − outputTokens)` | `cacheRead / (input + cacheRead)`（同口径） |
| **统计范围** | **当前会话**（页面显示「5 轮 765 步」） | **本进程全部请求** + 落盘 90 天日聚合 |
| 生命周期 | 随会话/引擎 | 内存账本**重启即清**（500 条上限），日聚合保留 90 天 |

⇒ 口径相同、**范围不同**；再叠加 ② 的看板翻倍 ⇒ 用户按时间段取增量比较时必然对不上。

**修复后**：同一会话、不重启、只发聚合模型请求的条件下，两边增量应当一致
（差别只剩缓存命中率的四舍五入位数）。范围差异（会话 vs 进程）是**设计差异**，
若要彻底"对得上"，需要产品层面统一（例如看板增加会话维度过滤）—— **本轮未做**。

## 7. 教训（本轮踩到的）

1. **"服务端不注册 + 客户端仍渲染"是最难发现的一类缺陷**：两侧各自都"正常"
   （宿主没报错、界面没崩），只有用户点开才发现。⇒ 这类"能力开关"改动必须同时改
   **可见性数据源**（registry / 清单），否则界面会长期撒谎。
2. **判据不能用被构建剥离的东西**：第一次验证用注释标记（`ledger-no-aggregate`）扫 `pack.js`
   得 0，差点误判成"修复没进产物"。**判据要落在功能形态**（`providers[0] === "aggregate"`）
   或**未被剥离的字符串字面量**（中文还被转义成 `\uXXXX`，得按转义形态或子串匹配）。
3. **幂等脚本的状态判定要逐项独立**：`patch-opencode-note.mjs` 初版要求"三处形态同时达标"
   才动手，而实际达标时机不同（补丁 D 会先写好 note）⇒ 混合态被判成结构异常**整体拒绝**，
   白跑一轮。改成逐形态独立后一次通过。
4. **"两次记账"这种缺陷最适合用逐条明细证伪**：聚合视图只能看出"两个 provider 数字一样"，
   而**明细成对**才是不可辩驳的证据（同一秒、同 token、不同 provider）。
