## 2. 本轮改动：订正 CSS 注释中被真机证伪的表述

### 2.1 为什么改

第五轮报告 §4.5 与交接文档 §3.5 都明确留档：

> 报告初版据上游 `collapsedWidth=56` 推为「224px 空白」，**真机证伪** ——
> inner root 被本层 `width:100%!important` 撑到 280px，折叠只让**文字消失**（23→0）。

但 `dsh-phone.css` 里那段注释**仍写着被证伪的旧说法**（L128-130）：

```
· 本层把侧栏容器宽度强制为 min(280px,86vw)（上面那条），而上游折叠态只渲染
  **56px 图标列**（layout 的 collapsedWidth=56，安卓）⇒ 用户在抽屉里点一下
  小按钮，侧栏折叠 ⇒ 容器 280px、内容 56px，差额 224px 就是那片空白
```

按交接文档「凡本仓库文档里写『折叠态 56px ⇒ 224px 空白』的地方，都应按此订正」，
本节就是落实这一条。**只改注释，不动任何规则**（规则本身上一轮已真机验证过）。

### 2.2 改后（L128-132）

```
· 本层把侧栏容器宽度强制为 min(280px,86vw)（上面那条），而上游折叠态会让
  **文字叶节点全部消失**（真机实测 23 → 0，只剩一排无标签图标）
  ⇒ 用户在抽屉里点一下小按钮，侧栏折叠 ⇒ 左侧变成「有宽度无文字」的空白带
  （⚠️ 2026-10-13 真机度量订正：**不是**「容器 280px、内容 56px、差额 224px」
  —— inner root 被上面那条 width:100%!important 撑满 280px，折叠只降密度不减宽度）
```

## 3. ⚠️ 本轮自己造成的一次事故（如实记录）

做反向破坏验证时，我用 node 脚本把三个「破坏样本」写回目标文件，**最后一次
`fs.writeFileSync(p, orig)` 用的 `orig` 是进入脚本时读的字符串 —— 但中途
`check()` 已经把文件写成 b3，而 b3 的构造用了 `orig.split(...).join(...)`。
问题在于：b1 的 replace 目标串里我写的是**带两个前导空格的规则行**，与实际文件
不一致 ⇒ `b1 === orig`（replace 没命中）；随后 b2/b3 的 split/join 命中了规则行
⇒ 写回了"规则被改坏"的版本，而最后的恢复又写回了 `orig`……**

**实际后果**：`dsh-phone.css` 在那几秒里处于「注释还在、两条规则行消失」的状态，
最终落盘的文件确实丢了规则（大小从 22861 掉到 22714 → 补回后 22861）。

**怎么发现与修复**：

1. 复跑 `ui-css-validate` 等全绿 —— **它抓不到**（CSS 结构仍合法，只是少了规则）；
2. 跑去跑「对照组」时判据1 意外报 red，才回头查文件；
3. 从远端 main 拉回该文件的完好版本作对照源，确认差异只有注释 3 行 vs 5 行；
4. 用字符串锚点把两行规则补回，再逐行 diff 确认「除预期注释差异外零差别」。

**修复后状态**（本地 vs 远端 main 逐行 diff）：

```
差异行 = L128-132（本地订正后 5 行） vs L128-130（远端旧 3 行）
其余 228 行完全相同，规则两行在位
```

**教训（与仓库既有「验证手段本身不可信」同型）**：
反向验证脚本「破坏—恢复」必须**先备份到独立文件、最后从备份恢复并断言相等**，
不能依赖内存里的 `orig`（构造破坏样本的表达式一旦没命中，样本就等于原文件，
后续写回顺序会把中间态落盘）。本轮已按此补了 `dsh-phone.css.bak2` 并断言一致。

## 4. ⚠️ 抓到自己工具链的一个真 bug（影响历史推送判定）

### 4.1 现象

`push-toggle.mjs` 与 `push-dsml.mjs` 的 DRY-RUN 审计显示
「本地=9ee84cba5e 远端=d3f587aba9（需更新）」，但两个文件的**内容逐字节相同**。

### 4.2 根因

两处脚本的 git blob sha 都写成了：

```js
// push-toggle.mjs:32 / push-dsml.mjs:11
crypto.createHash('sha1').update(`blob ${buf.length}\0`).digest('hex')
```

**只对 header（`blob <len>\0`）取 sha，没有把文件内容拼进去。**
⇒ 该值与文件内容完全无关，只取决于长度。实测：

```
内容 'hello world'（11 B）→ 脚本算法 1e6d396b2…  正确算法 95d09f2b1…
```

⇒ **同一个长度的所有文件都会算出同一个 sha**，于是「本地 vs 远端」的相等判断
对内容毫无分辨力。长度相同 ⇒ 恒判「无变化」；长度不同 ⇒ 恒判「需更新」。

### 4.3 影响面复盘

| 推送 | 文件数 | 长度是否全不同 | 判定是否被 bug 蒙对 |
|---|---|---|---|
| DSML（`47e5196338`） | 12 | 是（12 个文件体量差异明显） | **碰巧蒙对** |
| 抽屉修复（`e89a11f10f`） | 2 | 是（22627 vs 21333） | **碰巧蒙对** |
| 本轮 CSS 注释订正 | 1 | 是（22861 vs 22627） | **碰巧蒙对** |

⇒ 历史推送**没有漏推**（三次的长度都不同，bug 未造成漏推），但这是运气而非设计。

### 4.4 修复与判别力自证（本轮已完成）

两个脚本都已改为正确形式：

```js
const gitSha = (b) => crypto.createHash('sha1')
  .update(Buffer.concat([Buffer.from(`blob ${b.length}\0`), b]))
  .digest('hex')
```

**修后复跑 DRY-RUN**（实跑输出）：

```
main HEAD 21fda7157f｜DRY-RUN
  dsh-phone.css  22861 B  远端=9d52c1bb44 本地=f2faf784bf (需更新)   ← 正确
  apply.sh       21333 B  远端=d3f587aba9 本地=d3f587aba9 (无变化)   ← 正确
```

**push-dsml.mjs 修后**：12 个文件全部「无变化，无需推送」—— 与 §4.3 用正确公式
独立算出的结论一致。

**判别力自证**：同长度（100 B）不同内容 ⇒ sha 不同 ✓；
本地 apply.sh 的正确 gitSha 与远端 tree API 声明的 40 位 sha 完全相符 ✓。

⇒ 旧的「DRY-RUN 假绿」风险已消除。这两个脚本只住在本机 `.scratch/`，不进 git。

**本轮已用正确公式全量复核**：capsule 全部 154 个文件中 **153 个与远端 main
逐字节一致**，唯一不一致的就是本轮订正的 CSS（预期内）。

> ⚠️ 该 bug **已于本轮修好**（见 §4.4）：`push-toggle.mjs` 与 `push-dsml.mjs`
> 两处 `gitSha` 都已改为 `Buffer.concat([header, buf])` 的正确形式，
> 并复跑 DRY-RUN 验证（CSS 正确判「需更新」、apply.sh 正确判「无变化」、
> DSML 12 文件全部「无变化」、同长度不同内容 sha 不同）。
> **这两个脚本只住在本机 `.scratch/`，不进 git**，故无需提交。
