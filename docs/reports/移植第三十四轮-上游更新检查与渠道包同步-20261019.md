## 3. 执行与验证

### 3.1 步骤 4 首跑失败：适配锚点失效（**脚本按设计拒绝，设备零污染**）

```
════ [4] 施加 OFM 本地适配 ════
已施加  import（带过 channel-fetch）
已施加  apply 签名 + 网络层
已施加  cline 注入 fetcher
✗ gemini 注入 fetchImpl：锚点状态为 anchor-gone，拒绝改动（上游结构可能已变）
```

根因（读上游新源码）：上游 IKLTZ2 把 GeminiAuth 的接线从
`new GeminiAuth(ctx)` + `{ fetchImpl }` 改成 `new GeminiAuth(ctx, { fetchFor: geminiFetchForAccount })`
（**按账号取 fetcher**，见新增 `gemini-proxy.ts`），并把实例化点从 `gemini-adapter.ts`
搬进 `index.ts`（`apply()` 内，实测第 2051 行、缩进 2、全文件 `new GeminiAuth` 恰好 1 次）。

**危害边界已核实**：脚本第 180 行才写盘、失败在第 4 条即 `exit(1)` ⇒ 前 3 条**也没落盘**；
中止时设备 `pack.js` 仍为 `3885181 / 6d104719c43045c7`（未装、未备份、未回写工作区）。

### 3.2 修复：组合语义，而不是覆盖上游那一层

只改 `_ofm/patch-channelpack-port.mjs` 的 gemini 一条（其余 5 条锚点在新上游上仍 `待施加`，
`--check` 实测 exit 0）：

```ts
const gemini = new GeminiAuth(ctx, { fetchFor: (accountId: string) => {
  const perAccount = geminiFetchForAccount(accountId)
  return perAccount === fetch ? network.fetch : perAccount
} }) /* phone-port adapter: gemini */
```

| 情形 | 走的出口 | 为什么 |
|---|---|---|
| 账号**自己配了**代理 | 上游 per-account 解析（`proxyFetch`） | IKLTZ2 新能力，用户显式配置优先 |
| 账号**未配**代理 | OFM 本插件出口 `network.fetch` | 否则 OFM 出口在这一格被上游更新**静默顶掉** |

判据 `perAccount === fetch` 是**同引用**比较：上游无代理分支就是 `return fetch`
（`gemini-proxy.ts:72`），不是猜的。

## 6. 教训

1. **上游把一个注入点从"单 fetcher"改成"按账号解析器"时，适配不能机械换锚点** ——
   若照旧写 `fetchImpl: network.fetch`，会**覆盖掉上游新加的 per-account 代理**（用户功能缺失）。
   正确姿势是先读新 API 语义（`gemini-proxy.ts` 的 `createGeminiFetcherResolver`），再决定
   **组合**（本次）还是**退让**。
2. **锚点校验再次证明是止损阀**：`anchor-gone` 让脚本在**写盘前**中止，设备与工作区都保持原状
   （实测指纹未变）。若它"猜着改"，本轮就会把一个半成品产物装进设备。
3. **"产物没变"不能沿用上一轮结论**：§26.4 当时的结论是「该提交未改变产物 ⇒ 出厂副本无需同步」，
   本轮提交改了产物 ⇒ 出厂副本**必须**同步。判据要每次重测，不能复用。
