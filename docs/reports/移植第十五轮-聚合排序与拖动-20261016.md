## 2. 补了什么（三件事，宿主早就会、客户端一直没有界面）

| 端点 | 之前的界面 | 现在 |
|---|---|---|
| `aggregate.setOrderMode` | **无** | 顶部「排序：按临期／按手工」**单按钮**切换 |
| `aggregate.setOrder` | **无** | **鼠标拖动**候选自定义顺序 |

**实测宿主确实支持**（不是照文档猜的）：

```console
$ node hub-rpc.mjs aggregate.setOrderMode '{"mode":"manual"}'
{ "ok": true, "value": { "orderMode": "manual" } }

$ node hub-rpc.mjs aggregate.setOrder '{"canonicalId":"deepseek-v4-1-flash",
                                       "order":["workbuddy\u0000deepseek-v4.1-flash", …]}'
{ "ok": true, "value": { "canonicalId": "…", "order": [ … ] } }

$ node hub-rpc.mjs aggregate.rejectNonExpiring '{}'

```

⚠️ 顺序键是 **`provider\0realId`**（我一开始按 `provider` 单键提交，宿主照收但
`order` 回的是空数组 —— 因为对不上任何候选；换成双键后原样返回）。

## 4. 验证（这轮的重点是**验证器本身也返工了三次**）

### 4.1 新增能力：现在能验「点得对」

`check-aggregate-wiring.mjs` 从元素树里取出按钮，**真的调 `onClick`**，断言发出的 RPC：

```
点「未参与」开关      → aggregate.setAllowed {canonicalId, provider, realId, allowed:true}  ✓
点「排序：按手工」    → aggregate.setOrderMode {"mode":"expiry"}                            ✓
点「拒绝非临期」      → aggregate.rejectNonExpiring                                          ✓
```

**反向验证**（证明断言有区分力，不是摆设）：

```

未打 H 的旧文件         → ✗ 正确失败
```

### 4.2 ⚠️ 验证器三次返工（都是我的缺陷，如实登记）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | `rotationRosterOf is not defined` | 抽取函数用**写死的 12 个名字**，换面板后不够用 | 改成**依赖闭包**抽取 |
| 2 | `Unexpected token 'var'` | 闭包按「有同名 `function` 就行」判存在，把 `startCarrierContribution` **内部嵌套**的 `schedule()`/`tick()`/`ensureGuest()` 也拖了进来，切片首尾错位 | 加「是否顶层」判别 |
| 3 | `rotationRosterOf is not defined`（闭包只剩 1 个） | 「顶层」写成 `括号深度 === 0`，而**面板在深度 4、纯函数在深度 3**（esbuild 包装 + G 的 IIFE），两者不在一层 | 最终改用**行首缩进为 0** |

⚠️ 三次都是**验证器**的问题，**产品一直是对的**（那 21 个函数在 `client.js` 里
都有定义，已逐一核对）。若不查清就下结论，会把「验证器坏了」误报成「补丁坏了」。

### 4.3 另外两处判据也踩了「只认一代面板」

- `render-aggregate.mjs`：断言数「N 个渠道」，而 gitee 面板改成**候选平铺**，
  不再有那段文字 ⇒ 恒为 0 ⇒ **假红**。改为「三态文案至少出现一种」。
- `check-aggregate-wiring.mjs`：找按钮写死「默认不参与」，而 gitee 版叫
  **「无临期积分 · 未参与」** ⇒ **假红**。改为认两代文案。

> 教训同型：**验证器的判据必须跟着被测对象的版本走**，否则报的是自己的错。

### 4.4 补丁 I 与 H 的关系（已处理）

两者改**同一段**，I 是 H 的**超集**（gitee 版还多一个 `expiryWired === false` 分支）。
打 I 之后 H 的标记会消失 —— 这**不是坏了**。已让 H 的自检把这种状态识别为
「**已被补丁 I 取代（I 含 H 全部语义，正常）**」并**跳过**，不再报锚点错。

⚠️ 顺带堵掉一个真实风险：若 H 的 `--apply` 在这种情况下继续走，它会因
「`.pre-patch-h` 不存在」而**把 I 的产物当成原始文件备份** ⇒ 回滚再也回不到干净版。

## 6. 未做 / 待办（如实登记）

### ⚠️ 0. 关于「拖动在触摸设备上能否用」—— **我上一版把这条写过头了，已修正**

**原写法（错）**：我写了「拖动在这台设备上**很可能用不了**」，理由是「本机是触摸设备、
而代码零触摸回退」。**这个推断过强了**，本轮自我更正：

| 我当时的证据 | 为什么不足 |
|---|---|
| 代码只有 HTML5 drag、零 `onTouch*` | **这条成立**（硬证据，读源码） |
| 「本机是平板」⇒ 触摸设备 | ⚠️ **平板不等于没有鼠标** —— 蓝牙鼠标/触控笔在这类平板上很常见 |
| `getprop` 只有 touch HAL | ⚠️ `getprop` 看不到蓝牙外设；`/dev/input` 那次读的是 **Permission denied**（我已作废那条） |

**反证（更强的证据）**：你自己的原话是「我们不应该有上下箭头就是应该**鼠标**拖动」——
**你明确说的是「鼠标」**。而且这份代码里 `cursor: grab` 出现 **6 次**、
注释里提「鼠标」**8 次**、提「触摸」**0 次** —— 整套交互就是按鼠标设计的，
且**另外两处拖动（账号卡片、供应商开关）早已在用同一套 HTML5 drag**。

⇒ **结论改为**：拖动**大概率是能用的**（你本来就在用鼠标）；
我**不能**证明它不能用，只能证明「代码没有触摸回退」。
⚠️ 所以**不需要**为我这条推断去改产品 —— 除非你真的在**没有鼠标**的情况下试过拖不动。

**若真的拖不动**，那时再考虑（三个选项，按代价从小到大）：

1. **恢复上下箭头，但只在检测到无鼠标时显示**（`@media (hover: none)`）——
   桌面仍是你要求的鼠标拖动、无箭头；
2. **加触摸拖动**（`onPointerDown` + `setPointerCapture`）—— 统一桌面与触摸；
3. 维持现状（靠「按临期」自动排序 + 逐条开关）。

⚠️ 本条我**没有**改任何产品代码 —— 只是把一份过度推断的结论改正过来。

> ⚠️ **我最初还写过一条「`/dev/input` 下无鼠标设备」——那条证据无效，已删除**：
> 实际输出是 `Permission denied`（不是空目录），我把「读不到」当成了「不存在」。
> 这正是本仓库反复记录的**验证手段不可信**那一类错误。
> ⇒ 所以这里只说「**很可能**用不了」：硬证据是「代码只有 HTML5 drag、没有触摸回退」；
> **不能**据此断定你手上没有蓝牙鼠标/触控笔。

公开资料：
- [H5拖拽事件兼容性问题](https://ask.csdn.net/questions/9199034) —— 明确列出
  `dragstart/dragend` 在 **Android WebView「不稳定」**、iOS Safari「部分失效」，
  并给出「必须引入事件降级机制，优先使用触摸事件进行模拟」；
- [HTML5拖拽实现](https://www.php.cn/faq/2148829.html) —— 「iOS Safari：`draggable="true"`
  被忽略，`drag*` 事件全不触发；解决路径只有一条：检测 `ontouchstart`…」
