## 2. 补丁 J：徽标读数**双端点回退**

```js
readActiveProvider: async (canonicalId) => {
  try {
    const viaRoute = await callJetHub('router.activeRoute', …);   // 新端点（最实时）
    if (viaRoute?.provider != null) return viaRoute;
  } catch { /* 老宿主不认新端点 ⇒ 落到下面 */ }
  if (canonicalId === undefined) return { provider: null };
  return await callJetHub('aggregate.activeProvider', { canonicalId }); // 旧端点兜底
}
```

### ⚠️ 两个关键设计点（都是踩过/查过才定的）

1. **必须 try/catch**。`callJetHub` 失败是 **throw**（定义：
   `if (result?.ok === true) return result.value; throw new Error(...)`）。
   不接住的话，老宿主/异常路径下**回退永远不会执行** —— 而回退正是本补丁的全部意义。
   （我第一版就是这样写的，自查时发现。）
2. **回退必须传 `canonicalId`**，不能无参。无参时宿主回的是 `lastActiveProvider`
   （「任意虚拟模型最近一次成功」）—— 那正是你 2026-10-16 报障
   「用 glm5.3 显示的是腾讯 codebuddy」的成因。已读服务端实现核对：
   有 `canonicalId` 时读 `activeProviderByModel.get(canonicalId)`，**是分模型的**。

### 语义差异是刻意接受的

| | 新端点 `router.activeRoute` | 旧端点 `aggregate.activeProvider` |
|---|---|---|
| 写时机 | **转发一开始** | 整轮**成功**结束 |
| 含义 | 此刻正在用什么 | 上次成功用了什么 |

回退**只在新端点无数据时**发生，而那时本来就没「此刻」可显示
（未打 J 时会一直停在占位）⇒ 显示一个真实用过的渠道，明显优于占位。

**与上一轮宿主修复不冲突、可叠加**：重启后新端点有值，回退自然不再走。

### 4.1 本轮新增：**18 个渠道面板逐个渲染**（补上一处真实盲区）

`render-check.mjs` 只渲染外壳，而 `selected` 是 `useState` 初值 = **第一个渠道**
⇒ 它只证明了**那一个**渠道的面板不白屏。可是 17 家的能力不同
（`credits` / `creditPackages` / `permanentLock` / `usesExpiryWindow` /
`rateLimit` / `accountTest` …），面板会走**不同分支** ——
「1 个能渲染」**推不出**「17 个都能渲染」。

新建 `check-provider-panels.mjs`：把 `selected` 依次注入成每个渠道 id，
逐个真渲染。实测 **18 个全部通过**，HTML 长度互不相同
（55589 ~ 56229 字符）⇒ 每个渠道的面板确实走了自己的分支。

### 4.2 ⚠️ 这个工具第一次是**假绿**的（我必须记下来）

第一版把注入装在 `ReactCurrentDispatcher.current` 上，结果
**18 个渠道渲染出逐字节相同的 HTML（都是 55913 字符）**，
而脚本**照样打印「✓ 全部通过」** ——
一个「全绿却什么也没验」的假绿。

根因：**`renderToString` 会自己安装 dispatcher**，把外面装的那份覆盖掉。
修法照抄 `render-aggregate.mjs` —— 把代理过的 `React` **传给 `new Function`**
（编译期注入），`renderToString` 换 dispatcher 也换不掉组件闭包捕获的那个。

⚠️ 并**补了防假绿判据**：不同渠道的 HTML **必须互不相同**，
若全部相同就判定「注入没生效」并**失败**。现在它真的能区分了
（未打 G 的旧文件 ⇒ 正确失败）。

### 4.4 补丁 J 的**无参分支**是防御性的（已核对可达性）

补丁 J 里有一句 `if (canonicalId === undefined) return { provider: null }`。
逐处核对 `readActiveProvider` 的**真实调用点**（区分注释与代码）后确认：

```
[1] @5460 代码  readActiveProvider = props.readActiveProvider   ← 取值
[2] @5487 代码  const [activeProvider…                          ← 取值
[3] @5790 注释  （解释依赖数组的历史缺陷）
[4] @6829 注释  （用户报障原文，描述**旧**的无参调用）
[5] @7403 代码  typeof readActiveProvider !== 'function'        ← 守卫
[6] @7712 代码  readActiveProvider(modelId)                     ← **唯一的真调用，带参**
[7] @8375 代码  依赖数组
```

⇒ **唯一的真调用永远带 `modelId`**；无参分支**不可达**，纯属纵深防御
（老宿主/未来调用方若真无参，返回 `null` 比返回 `lastActiveProvider` 更安全 ——
后者正是「显示别的模型的渠道」那个报障的成因）。
