### 1.2 这条线在代码里长什么样（关键结构，之前文档未写清）

```
runtime/                       ← 上游仓库内容（与 jwoo 上游逐字节一致，1121/1121 实测）
├── package.json               ← 钉 "@deepseek-ai/dsh": "0.2.1-alpha.1"
├── pnpm-workspace.yaml        ← nodeLinker: hoisted + 三个 override
├── pnpm-lock.yaml             ← 620660 B，全量解析结果
├── stubs/{koffi,node-pty,sharp}   ← Android 无原生变体 ⇒ 万能桩
├── tools/pnpm/                ← 内置 pnpm 10.34.6（APK 自带，不依赖用户环境）
└── overlays/@deepseek-ai/     ← ★ 23 个包的 Android 适配补丁（40 文件）
```

**overlays 的作用机制**（`scripts/build-assets.py:153`）：

```python
for overlay in (DEPLOY / 'overlays').rglob('*'):
    if overlay.is_file():
        shutil.copy2(overlay, MODULES / overlay.relative_to(DEPLOY / 'overlays'))
```

⇒ 引擎以 **npm 包**安装到 `runtime/node_modules`，overlays 里的同名文件**覆盖安装产物**，
再打包成 `dsh-tree.tar` 进 APK。所以「升级引擎」必须**同时重做 overlays**，
否则 Android 适配（bash 路径 / flock 原子发布 / 会话落盘）整块失效。

## 5. 升级风险面：逐项实测结论

### 5.1 ★ vendor tsc：零新增类型错误（决定性证据）

这是评估报告 §6.2 列为「未验」的最大残余风险（overrides 43 文件在新版能否编译）。

搭沙箱：`本地镜像 vendor/dsh-providers-hub` + `胶囊 files/`（34 文件）+ `胶囊 overrides/`（71 文件），
分别以 **alpha.1 类型**与 **alpha.2 类型**跑 `tsc -p tsconfig.json --noEmit`：

| 引擎类型 | 输出行数 | 内容 |
|---|---|---|
| `0.2.1-alpha.1` | 6 | `src/qoder-wasm.ts(643,43): error TS2345 …` |
| `0.2.1-alpha.2` | 6 | 同上 |

```
diff tsc-a1.txt tsc-a2.txt
✅ 逐字节完全一致（零新增类型错误）
```

> 那 1 条错误是 **既有基线**（`PORTING-GITEE-HANDOFF.md` 多处记载的 TS 版本差异），
> 与引擎版本无关 —— 两版输出相同即证。

### 5.2 ★ 胶囊 27 个 spec：747 passed / 0 failed

设备上 esbuild 原生二进制**无法执行**（`/data/data` 是 `noexec`，且 Android 拒绝从应用数据目录执行原生码）。
故自建极简 vitest 替身（`.scratch/engine-a2/vitest-shim.mjs`）+ Node loader：

- 覆盖 `describe/it/expect/beforeEach/afterEach/vi.fn/vi.mock/vi.stubEnv/vi.stubGlobal` 等；
- 关键：`vi.mock` 必须**在 load 阶段预扫**（ESM 先解析静态 import 再执行模块体，而 vitest 的 `vi.mock` 是提升的）；
- `.ts` 用 TypeScript 编译器 API 真实转译（绕开 esbuild）。

**结果**：`747 passed / 0 failed` —— 与第九轮 CI 实测的 `Tests 747 passed` **数字完全一致**。

> ⚠️ **开发中修掉替身自身 3 个缺陷**（否则会给出假红/假绿）：① 从不执行 `beforeEach`
> （状态跨用例泄漏 ⇒ 3 处假红）；② `toThrow` 不认正则；③ `run()` 用 `?t=` 清缓存导致
> `load` 钩子的 `$` 锚定正则漏判（`vi.mock` 预扫整块失效）。三者都属「验证手段本身不可信」。

## 12. ⚠️ 事故复盘：Jet Hub 整块消失（用户报障，同日修复）

> **本节是事后追记**（用户报障后补写）。它记录的是**本轮移植引发的真实生产事故**，
> 以及为什么本轮的验证**全部绿灯却漏掉了它**。

### 12.1 现象与用户侧修复

用户把本轮构建的 APK 装机后报障：**「jethub 插件不见了」** —— 输入区最下方的
「在用模型」实时读数胶囊整块消失，而 App 其余部分正常。

用户随后**自行**通过另一台设备定位并修复（远端提交 `46e2cb7f94`，18:23）：

```
fix(capsule): vendor 插件 peer 版本同步到 alpha.2，修 Jet Hub 被引擎静默跳过
```

### 12.2 根因（已用引擎源码逐行确认）

引擎的插件兼容门禁在 `@deepseek-ai/dsh-app-boot/lib/index.js:286`：

```js
function evaluatePluginCompatibility(manifest, exemptions = {}, runtimeVersion = getDshRuntimeVersion()) {
  ...
  if (requirement.trim() === "" || !semver.satisfies(runtimeVersion, requirement, { includePrerelease: true })) peers[name] = range;
```

而 `loadProfileDirectory`（第 1011 行）对不兼容的处理是 **`throw`**：

```js
const issue = evaluatePluginCompatibility(bundleManifest, exemptions);
if (issue !== undefined && !issue.exempted) throw new Error(pluginCompatibilityWarning(issue));
```

链条：
1. 引擎升到 `0.2.1-alpha.2`；
2. `vendor/dsh-providers-hub/package.json` 的 `peerDependencies["@deepseek-ai/dsh-llm"]`
   仍**精确**钉 `0.2.1-alpha.1`（不是 `^` 范围）；
3. `semver.satisfies('0.2.1-alpha.2', '0.2.1-alpha.1')` = **false** ⇒ 判不兼容；
4. 抛错 ⇒ **整个 profile bundle 被跳过**（启动日志仅一行）。

### 12.3 ★ 为什么本轮验证全绿却漏掉

这是本次事故最值得记录的部分。本轮做的验证是：

| 验证 | 判据性质 | 为什么没抓到 |
|---|---|---|
| `tsc --noEmit`（alpha.1 vs alpha.2） | 编译期类型 | 类型没变，本来就该绿 |
| 747 个 spec | 单元行为 | 门禁在**装配期**，spec 不装配 profile |
| UI 哈希 + 槽位契约 | 静态串匹配 | 与 peer 版本无关 |
| `apply.sh` 全量门禁 | 文件/接线自检 | **没有一条检查 peer 版本** |
| 端到端 `apply.sh` | 构建脚本 | 构建成功 ≠ 运行期能装配 |
| APK 产物 9/9 验收 | 包内内容 | 只验了「文件在不在」，**没验「引擎会不会加载它」** |

**共同盲区**：本轮所有证据都是**编译期/静态**的，而门禁**只在运行期生效**。
`runtime/overlays` 那段我改得再对，也管不到另一个文件的 `peerDependencies` 字段。

> 教训与仓库既有纪律同型：**「构建绿」证明不了「能跑」**。
> 上一轮我验的是「文件铺对了吗」，缺的是「引擎愿意加载它吗」。

### 12.4 修复（用户版，已确认有效）

新增胶囊覆盖 `overrides/vendor/dsh-providers-hub/package.json`，把
`peerDependencies` 与 `devDependencies` 的 `@deepseek-ai/dsh*` 同步到 `0.2.1-alpha.2`；
并在 `apply.sh` 加 §5.95 自检（三行 grep 钉住 Jet Hub 的 peer）。

用户特别点出 dev 同步的**第二重价值**：`rebuild-vendor.sh` 会用 alpha.2 的类型编译，
真 API 不兼容就会在 **CI 编译期**报红，而不是在设备上静默消失。

**实测确认**（用引擎自身的判据函数逐个判定 profile 实际加载的 6 个 bundle）：

| bundle | 判定 |
|---|---|
| `@deepseek-ai/dsh-base` / `dsh-web-app` | ✅ 放行 |

### 12.5 后续修复：同类地雷的泛化排查（本轮补做）

用户修的是**一个包**，但事故的**成因是普遍的**。故按「先查证再动手」做全量扫描
（范围 = `runtime/package.json` 的全部 `file:` 依赖 = `build-assets.py` 打进 APK 的插件集合）：

**发现 `dsh-channel-qq` 仍钉 `0.2.1-alpha.1`** —— 与 Jet Hub 事故**完全同型**
（`peerDependencies["@deepseek-ai/dsh-llm"] = "0.2.1-alpha.1"`，精确版）。

**但它当前不发作**。逐条核实了三条门禁路径：

| 路径 | 是否约束 `dsh-channel-qq` | 依据 |
|---|---|---|
| `loadProfileDirectory` | ❌ 不经过 | 只遍历 `profile.bundles`；它**不在**该列表（列表：dsh-base / dsh-web-app / dsh-providers-hub / dsh-phone-account / dsh-phone-qq / @zseven-w/dsh-noema） |
| `preflight(rows)` | ❌ 不经过 | 只查 patch 组合出的 entry；它的 `cordis.patch.yml` 是空数组 `[]`，不作为 row 出现 |
| 运行期 `ctx.plugin()` | ❌ 不经过 | 由 `phone-qq/index.js:105` 的 `await import('dsh-channel-qq')` 动态加载，无门禁 |

⇒ 定性为**潜伏地雷，不是现症**。**未观测到 QQ 功能异常**，不把它说成"QQ 也坏了"。
但一旦被加进 `bundles`/patch，立刻复现同类事故。

### 12.6 本轮补做的两件工具（防同类）

**① `scripts/check-plugin-peers.mjs` —— 不列举，而是泛化扫描**

§5.95 只钉住 Jet Hub 一个包（列举式，只能防已踩过的）。本脚本改为：
- **覆盖范围**：扫 `runtime/package.json` 全部 `file:` 依赖（当前 8 个插件）；
- **判定权威**：优先用**引擎自身的** `evaluatePluginCompatibility`
  （复用真判据，不自实现 semver）；无引擎树时用 semver 等价判定；
- **semver 来源**：**仓库自带 pnpm 里的那份**
  （`runtime/tools/pnpm/dist/node_modules/semver`，随仓库提交）⇒
  CI 在 `pnpm install` **之前**也能跑真判定；
- **判据缺失时显式 `exit 2`**，而不是退化判定。

> ⚠️ **开发中踩到的假红（留档）**：首版在取不到 semver 时**退化为精确串比对**，
> 于是 noema 的 `^0.2.1-alpha.1` 被误判成失配 ⇒ **构建期假红**。
> 这与仓库反复记录的「验证手段本身不可信」同型，故改成上述「自带 semver + 缺判据即报错」。

**② `ui-tests/plugin-peers.test.mjs` —— 判别力反证**

该门禁的失效形态恰恰是**「静默变恒真」**（判定写错就永远绿，而设备上照样消失）。
故双向断言：

| 方向 | 断言 |
|---|---|
| 能检出 | 精确旧版 `0.2.1-alpha.1` / 未来版 `9.9.9` / 不存在版 / 空范围 / 非法范围 / 多 peer 单个不合 |
| 不误报 | caret `^0.2.1-alpha.1`（noema 真实写法）/ tilde / `>=` / `workspace:^` / `*` / 非 dsh 的 peer / 无字段 / 空对象 |

**③ `apply.sh` §5.97**：门禁 + 反证都进构建期。

### 12.9 给后续维护者的三条纪律（本次事故的沉淀）

1. **引擎升级后，除了改 `runtime/`，必须扫一遍所有插件清单的 `peerDependencies`**。
   `@deepseek-ai/dsh*` 钉**精确版**的包会被静默跳过；用 `^` 才安全。

2. **「构建绿」不等于「能跑」**：装配期门禁只在运行期生效。引擎类升级后，
   必须补一次**真机启动**观察（本次事故只有真机能发现）。
3. **列举式自检只能防已踩过的坑**。同类风险要用**泛化扫描**（§5.97 的做法），
   并给门禁配**判别力反证**（防「静默变恒真」）。
