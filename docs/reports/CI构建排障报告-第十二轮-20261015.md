## 1. 五处缺陷逐条详情

### ① files/ 下 3 个 spec 的远端残留（F-03 门禁失败）

**CI 报错原文**：

```
##[error]capsule files/ 下有与上游工作树同路径的文件（会静默覆盖上游内容，Issue F-03）。
##[error]若确实要覆盖上游同名文件，请把它移到 overrides/（那是覆盖的既定位置）：
vendor/dsh-codearts-auth/tests/unit/aggregate-adapter.spec.ts
vendor/dsh-codearts-auth/tests/unit/auto-adapter.spec.ts
vendor/dsh-codearts-auth/tests/unit/badge-model.spec.ts
```

**根因**：第十一轮把这 3 个 spec 从 `files/` 迁到 `overrides/`（F-03：显式登记
"这是有意的覆盖"），**本地已删除**，但推送工具 `.scratch/live/tools/push-capsule.mjs`
按设计**只做新增与更新、永不删除**（其文件头明确写着"删除 0（本脚本永不删除远端文件）"）。
⇒ 本地删除的语义没有传达到远端。

**为什么必须删**（不只是门禁洁癖）：远端残留的是 **F-04 修复前**的旧副本
（用单个 `lastContextTokens` 字段；`aggregate-adapter.spec.ts` 旧版 2799 行 vs
新版 2812 行，差异在 `SPEC_SESSION_ID` 与按会话分桶）。留着会**遮蔽**新测试。

**修法**：用 Git Data API（blob → tree → commit → 更新 ref）**原子提交**删除。

### ② F-68 门禁在 CI 拿不到 typescript

**CI 报错原文**：

```
✗ 找不到 typescript（试过 DSH_TS / DSH_TREE / 设备树 / 包的 node_modules）
    用法：export PATH=/data/data/com.dshphone/files/bin:$PATH（设备树 TS 在 $DSH_TREE/node_modules/typescript）
##[error]Process completed with exit code 1.
```

**根因**：`apply.sh` 在 workflow 步骤顺序上**早于** `安装 pnpm` 与
`编译 vendor 插件（rebuild-vendor.sh）`，而 vendor 的 devDependencies（含 typescript）
要到后者才安装。脚本原先按"判据缺失 ≠ 通过"硬 `exit 1` —— 纪律本身正确，
但它没考虑"**判定时机**可以后移"。

**修法**（不削弱判别力）：

1. `check-capsule-artifacts.mjs`：`GITHUB_ACTIONS=true` 且未声明
   `CAPSULE_ARTIFACT_GATE_REQUIRED=1` 时打印「⏭ 跳过」并 `exit 0`；
   带该变量时缺 TS 仍是**硬失败**；本机/非 CI 缺 TS 仍硬失败（原纪律不变）。
2. `build-apk.yml`：在 `编译 vendor 插件` 之后新增
   「门禁：胶囊产物与源码一致（F-68）」步骤，置 `CAPSULE_ARTIFACT_GATE_REQUIRED=1`
   并显式 `DSH_TS` 指向 vendor 的 typescript；纯净构建（DISABLED）打印警告后跳过。
3. `apply.sh`：6.3) 注释同步说明该延迟机制。

**本机验证**（用 fs 拦截钩子复现"CI 无 typescript"条件，逐条验四分支）：

| 场景 | 期望 | 实测 |
|---|---|---|
| CI 且无 REQUIRED | 跳过 rc=0 | ✅ rc=0，打印「⏭ 跳过」 |
| CI 补跑步骤缺 TS | 硬失败 rc=1 | ✅ rc=1，提示补跑点必须真跑成 |
| 非 CI（本机）缺 TS | 硬失败 rc=1 | ✅ rc=1 |
| 本机正常 | 通过 rc=0 | ✅ rc=0（ts 5.9.3，两份产物逐行一致） |

### ③ context-window-learn.spec.ts 断言旧实现

**CI 报错原文**：

```
FAIL tests/unit/context-window-learn.spec.ts > 聚合层接线（源码文本断言）> **截断也算证据**…
AssertionError: expected '…' to contain 'self.lastContextTokens = Math.max(sel…'
Test Files 1 failed | 25 passed | 1 skipped (27)
     Tests 1 failed | 746 passed | 11 skipped (758)
```

**根因**：断言钉的是 F-04 修复**前**的进程级只增峰值写法。F-04 已把该字段改成
**按会话分桶**（`lastContextTokensBySession`）：请求内取 max 落局部变量 `requestTokens`，
落桶交给 `recordSessionContextTokens`（**覆盖**语义，会话被压缩变小后观测值能如实下降）。

**修法**：断言同步到新写法，并补反向断言钉住旧字段不得回来。

**本地验证**：修复后 `context-window-learn` **通过 88 / 失败 0**；反向验证
（把断言回退成旧写法）⇒ **该用例变红**（1 failed），恢复 ⇒ 88 全绿。

**同时修掉两个验证装置盲区**（这正是该失败此前没被本地发现的原因）：

- `run-specs.sh` 只遍历 `overrides/` 下的 spec，而这条在 `files/` 下 ⇒ 现**两处都跑**；
- 本地 vitest 兼容层**缺 `beforeEach` 导出** ⇒ 现支持（含顶层 hook 与 describe 作用域）。

### ④ MainActivity.kt 的 Kotlin 断句（真实代码缺陷）

**CI 报错原文**：

```
e: …/MainActivity.kt:462:13 Syntax error: Expecting an element.
e: …/MainActivity.kt:463:13 Condition type mismatch: inferred type is 'Int' but 'Boolean' was expected.
> Task :app:compileDebugKotlin FAILED
```

**根因**：F-29 通知权限那段把 `==` 放在**行首**续行，而 Kotlin **不把以运算符起头的
下一行视为续行**：第 461 行 `val granted = checkSelfPermission(...)` 已语法完整，
下一行的 `==` 被解析成新语句。

```kotlin
// ❌ 修复前
val granted = checkSelfPermission(android.Manifest.permission.POST_NOTIFICATIONS)
    == android.content.pm.PackageManager.PERMISSION_GRANTED

// ✅ 修复后（Kotlin 官方风格：运算符留在上一行尾）
val granted = checkSelfPermission(android.Manifest.permission.POST_NOTIFICATIONS) ==
    android.content.pm.PackageManager.PERMISSION_GRANTED
```

**为什么此前没发现**：本机无 Android SDK / Kotlin 编译器，`apply.sh` 的全部离线门禁
与本地 spec 都**不编译 Kotlin**；而前几轮 CI 都卡在更早的步骤，这是**第一次**走到
Gradle 编译。

**同类形态全仓排查**：对胶囊内全部 `.kt` 做"括号深度 0 处、非注释行、以
`==/!=/&&/||/<=/>=/+/-/*///%/< />` 起头"扫描 ⇒ **0 处**（仅此一处，已修）。

### ⑤ aapt 不在 runner PATH（门禁假红）

**CI 报错原文**：

```
BUILD SUCCESSFUL in 2m 5s          ← APK 编译其实是成功的
line 1: aapt: command not found
##[error]Process completed with exit code 127.
```

**根因**：`aapt` 位于 `$ANDROID_HOME/build-tools/<ver>/` 下，**不在** runner 的 PATH 上。
⇒ 门禁**假红**：它压根没判定产物，而是自己找不到工具就失败了。

**修法**：

```bash
AAPT="$(ls -d "$ANDROID_HOME"/build-tools/*/aapt 2>/dev/null | sort -V | tail -1 || true)"
# 兼容新版 build-tools 只随附 aapt2 的情形
[ -n "$AAPT" ] && [ -x "$AAPT" ] || AAPT="$(ls -d "$ANDROID_HOME"/build-tools/*/aapt2 2>/dev/null | sort -V | tail -1 || true)"
# 判据缺失 ≠ 通过：两个都找不到 ⇒ 硬失败（这是发布前唯一防线）
```

**本地验证**（三分支，逐字照抄门禁逻辑、只把"执行 aapt"换成 node 桩）：

| 场景 | 期望 | 实测 |
|---|---|---|
| 多版本 build-tools | `sort -V` 选最高版本，判非 debuggable | ✅ 选中 36.0.0，rc=0 |
| 产物含 `application-debuggable` | 硬失败 rc=1 | ✅ rc=1 |
| 工具缺失 | 硬失败 rc=1（打印候选目录） | ✅ rc=1 |

另确认 `sort -V` 在本机 toybox 与 runner 的 GNU coreutils 上都可用。

## 2. 额外加固：F-68 门禁的「补跑点」不得消失

②的修法引入一个**新的失效形态**：F-68 在 `apply.sh` 里变成"跳过"，其真正判定
落在 workflow 的补跑步骤上 —— 这正是本项目一路在防的"**看起来跑了，其实没判定**"。
一旦补跑步骤被误删或改名，CI 会**全绿地失去这道门禁**（`apply.sh` 里那次调用
不带 REQUIRED，跳过不报错）。

故在 `apply.sh` 的 F-01 段之后增加断言（沿用"钉胶囊模板、运行期一致时才断言"的既有风格）：

```bash
grep -qF -e "CAPSULE_ARTIFACT_GATE_REQUIRED" .github/capsule/build-apk.yml
grep -qF -e "check-capsule-artifacts.mjs" .github/capsule/build-apk.yml
```

**有牙验证**：从模板删掉该步骤 ⇒ 两条断言均失败（符合预期）；完好模板 ⇒ 均命中。

## 3. 为什么推送需要原子提交（工具事实登记）

`build-apk.yml` 的触发器是 `on: push`（无 paths 过滤）且
`concurrency: cancel-in-progress: true`。⇒ 多文件修复若逐文件 PUT，会**连续推送、
互相取消**，最终那次运行是否包含全部改动要靠运气；而②的修法要求
「`apply.sh` 的跳过逻辑」与「workflow 的补跑步骤」**同时生效**（只推一个 =
门禁两边都不跑）。故本轮全部改用 Git Data API **单个 commit 原子提交**。

另登记两个既有事实（本轮踩到）：

1. `.github/workflows/build-apk.yml` 是 `capsule/build-apk.yml` 的**铺开产物**，
   唯一复制点是**手动的** `sync-upstream.yml`。⇒ 胶囊模板更新后必须**手工一并同步**
   该文件，否则 CI 跑的仍是旧 workflow（本轮第一次推送就因此让 F-01 门禁没生效）。
2. `push-capsule.mjs` **不删除远端文件**。凡在本地删除/迁移胶囊文件，
   必须另用 Git Data API 补一次删除提交，否则远端残留（①即此）。

## 5. 遗留与建议（未在本轮改动）

1. **`aapt dump badging` 的版本选择**：本步依赖 `$ANDROID_HOME/build-tools/*` 下存在
   `aapt` 或 `aapt2`。runner 镜像目前提供 `37.0.0`，但**上游若移除 aapt 只留 aapt2**，
   新版 `aapt2 dump badging` 输出格式是否完全兼容**未经验证**（本轮无该环境）。
   建议下次镜像变更时留意该步骤的输出行。
2. **`ui-tests/ci-compat.test.mjs` 的超时风险**（静态审计指出，**未在真实 CI 复现**）：
   它以 120s 超时判失败，而被它 spawn 的部分工具自身超时更长
   （`ui-audit-objectives.mjs` 300s、`ui-verify-installed.mjs` 180s），
   且 `ui-verify-preview-equivalence.mjs` 会真发 GitHub API 请求。网络慢时可能误红。
   本轮运行该步**通过**，故未改动。建议后续为其增加 `GITHUB_ACTIONS` 短路或提高超时。
3. **真机验收清单**：第十一轮报告 §5 的 12 项仍待真机逐项确认
   （本轮只证明"能构建出包"，不证明 UI 行为）。
4. **首次完整构建耗时**：本次因命中 jniLibs 缓存（NDK/原生步骤 skipped）约 3 分钟；
   冷缓存时需下载 NDK 与编译 Rust 三件套，预计显著更长。

## 6. 结论

- 用户报告的「构建失败」实际是**五层缺陷叠加**，逐层修复后**构建全绿**并产出 APK。
- 其中 **④ 是真实代码缺陷**（Kotlin 断句，会让 App 无法编译），不是配置问题；
  ①②③⑤ 分别为推送工具语义缺口、两处 CI 环境假设错误、一处测试未跟上实现。
- 每处修复都做了**可复跑验证**，③与新增断言另做**反向验证**（回退必红）。
- 已额外加固 1 条（F-68 补跑点断言），并如实登记 3 项遗留（§5），
  其中 §5.2 明确标注「静态审计结论、未在真实 CI 复现」。
