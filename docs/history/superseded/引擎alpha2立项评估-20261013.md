## 3. 三项必须实测确认的风险（按 severity 排序）

> **⚡ 阅读提示**：本节写于阶段 0 之前。**§8 已给出其中 2.5 项的答案**
> （§8.1 回答了 §3.2、§8.2 回答了 §3.1 的 30/31、§8.4 顺带排除了一批删除）。
> 保留原文以便对照「评估思路」与「实测结论」的差异。

### 3.1 ★★★ 构建产物的哈希是否重生（最高风险）

**现象**：`SidebarRoot.module.css` 在 alpha.2 改了 1 条规则 ⇒ 源文件 sha 变 ⇒
**CSS Module 的构建期哈希极可能重生** ⇒ `hHd-Xa_*` 变成别的串。

**为什么不能只看源文件**：源 CSS 里是语义类名（`.collapsed` / `.newSession`），
`hHd-Xa_` 是构建时才生成的。我在源文件层验证不了它。

**为什么这是最高风险**：壳侧 55 个哈希里 `hHd-Xa_*` 只占 2 个，但**本轮刚修的
「抽屉内禁用上游 toggle」规则恰恰锚在 `.hHd-Xa_toggle` 上**（`dsh-phone.css` 新增规则 +
`apply.sh` 两条自检）。哈希一重生，该修复**静默失效**，用户报障的「菜单与小按钮冲突」
立刻复发 —— 而 `apply.sh` 自检只验「规则在 CSS 里」，**验不了「哈希在引擎里还存在」**
（那需要 `--tree` 在线模式，CI 没有引擎树）。

**确认方法**：拿 alpha.2 源码构建出 `lib/client.js`，grep 哈希串，与设备树（alpha.1）比对。
**成本**：需在 CI 或本机复刻上游构建（esbuild + 其 CSS 管线）—— 这是立项的主要工作量。

### 3.2 ★★ 槽位契约是否仍被声明

alpha.2 的 `dsh-client-ui-conversation` 文件数没变（120 → 120），但**内容变更未知**。
若 `conversation.header.leading` 的声明形态变了（kind/scope），抽屉开关会不渲染。

**确认方法**：拉 alpha.2 的 `ui-conversation/lib/client.js`，grep `registerHeader` 段
与 alpha.1 比对。**成本低**（单文件比对，1 次 API + diff）。

### 3.3 ★★ `dsh-web-frontend` 的启动契约

壳子的 `home-template` / `profiles` 与引擎 boot 流程耦合（`window.__DSH_BOOT__`
由 `dsh web` 注入）。alpha.2 的 `apps/web/package.json` version 已跃迁，
若 boot 注入点或模块表形态变了，壳子可能起不来。

**确认方法**：比对两版 `packages/bundle` / `apps/web/src` 的入口与 `__ModuleLoader__` 协议。
**成本中**。

### 8.3 仍未消除的**一个**不确定（如实标注）

**构建期哈希是否会因为「文件内容变了」而重生。**

- 上游 CSS Module 管线是「源 `.module.css` → `.module.css.mjs` → 内联进 `lib/client.js`」，
  语义类名在构建时被替换成 `hHd-Xa_*` 这类串；
- 我**无法从源文件层**证明该替换用的是「内容 hash」还是「稳定映射」——
  若是前者，SidebarRoot 内容改了 1 条规则就可能让**整个文件**的哈希串全变；
- 官方 release **无预编译产物**（assets 为空），所以也不能靠下载 alpha.2 的 `lib/` 来直接比对。

**这个不确定的影响面**：只有 `hHd-Xa_*` 这 2 个哈希（`_toggle`、`_root`）+ `_footArea`。
而 `_toggle` 恰恰是**本轮刚修的「抽屉内禁用」规则**所锚定的 —— 它一失效，
用户报障的「菜单与小按钮冲突」会复发，且 `apply.sh` 自检**抓不到**
（自检只验「规则在 CSS 里」，不验「哈希在引擎里还存在」）。

**消除它的最小成本**：在 CI 加一个 job，用 alpha.2 源码构建 `dsh-client-ui-sidebar`
单包（`pnpm --filter @deepseek-ai/dsh-client-ui-sidebar build`），grep 产物里的哈希串。
**约 10 分钟**，且不需要动壳子任何代码。

### 8.4 ⚠️ 一次被数据截断骗到的误判（留档）

初版评估据「递归树 API」算出的差异是 **725 文件 / packages 零删除**。
后来全量逐层遍历两版完整树（alpha.1 14208 blob、alpha.2 14988 blob），真实数字是：

| 指标 | 截断数据（错） | 全量数据（对） |
|---|---|---|
| 总变更 | 725 | **3357**（新增 935 / 删除 155 / 内容变更 2267） |
| `packages/` 删除 | 0 | **148**（分布在 11 个包） |

**被删的 11 个包**：`hooks/hook-protocol`(19)、`webhook`(28)、`subagent`(20)、
`session-query`(13)、`terminal`(11)、`skill`(9)、`workflow`(8)、`session`(7)、
`bundle`(1)、`experimental`(1)、`lsp`(1)。

**精确核对（按 package.json 的 name 对设备树 279 个包做交集）：壳侧一个都没用到。**

> 教训：node 的 `JSON.parse` 对大响应会静默截断（不报错，只给半截数据），
> 而半截数据推出的结论**看起来完全合理**。这与本仓库反复记录的
>> 「验证手段本身不可信」同型 —— 已把「逐层遍历 + 与另一独立来源交叉核对」
> 列为大数据比对的必要步骤。
