## 2. 最重要的一条约定：胶囊（capsule）架构

**这是本工程的核心，不理解它会得出完全错误的结论。**

```
git 仓库（main）
├── 上游内容（vendor/、app/ 等）  ← **永不直接改动**
└── .github/capsule/              ← 全部自有代码的**源材料**
```

**构建时**（`build-apk.yml`）：

```
1. bash .github/capsule/apply.sh        ← 把 files/ 与 overrides/ 铺到工作区（临时，git 无感知）
2. rebuild-vendor.sh                    ← 重编 vendor 插件
3. python3 scripts/build-assets.py      ← 同步资源到 phone-qq/ 与 peer/
4. ./gradlew :app:clean :app:assembleDebug   ← **真编译 Kotlin**（CI 是唯一能编译的地方）
5. gh release create                    ← 发 Release
```

**为什么这样做**：`sync-upstream.yml` 合并上游时**看不到胶囊改动** ⇒ 既不会被覆盖，
也不会破坏未来的上游更新。

> ### ⚠️ 三个由此产生的坑（都实测踩过）
>
> **坑 1：直接读 `app/src/main/assets/dsh-phone.js` 会得到 25521 B 的旧基线版。**
> 本层产物在 `.github/capsule/overrides/app/src/main/assets/`（33754 B）。
> 构建时才铺到 `app/`。**核对产物时必须用 capsule 路径**。
>
> **坑 2：`ui-verify-installed.mjs` 读 APK、`ui-live-verify.mjs` 读 WebView——两者口径不同。**
> APK 是权威（设备装的是什么）；WebView 可能被**注入污染**（页面里跑的是注入产物）。
> 两者矛盾时**以 APK 为准**。用 `--cross-check` 可让两者在同一输出里对齐。
>
> **坑 3：设备上有两条注入路径**（`MainActivity` 与 `phone-qq` 的 `tapIndex`），
> 各自注入一次同一份代码。做注入实验时必须**同时处理两条**，否则页面里会有两份不同版本。

### 3.3 ADB 层：**只差一条人类消息**

**为什么差**：`phone_control` 工具处于**停止态**，而解除它需要
`phoneControlIntent` 更新 —— 该状态**只在三种事件更新**：

```js
// dsh-phone-control/index.mjs（源码依据）
(event.type === 'user/message' && event.data.source?.kind === 'user')
  || (event.type === 'sandbox/mode' && event.data.source !== 'delegation')
  || event.type === 'permission/preset'
```

而 `goal-round` 的**自动续跑不产生 `user/message` 事件** ⇒ 停止态解不开。
**这是有意的安全设计**（防自动续跑滥用手机权限），不是缺陷。

**怎么做**：由人类在会话里**发一条真实消息**（哪怕只说"继续"），或切换一次权限预设。
之后即可执行 `scripts/ui-adb-layer-plan.md` 里的步骤：

```
1. phone_control launch com.dshphone
2. phone_control screenshot        → 记尺寸，确认当前页
3. phone_control read              → 找开关节点（优先用 nodeId 而非裸坐标）
4. phone_control click(nodeId)     → **系统级**点击
5. phone_control screenshot        → 看像素，确认抽屉滑出
6. phone_control tap(遮罩区)        → 系统级点击遮罩
7. phone_control screenshot        → 确认收回
```

**ADB 层专属判定**（浏览器层测不到）：

- [ ] 开关能被**系统级**点击命中（不经浏览器注入）
- [ ] 抽屉滑出后在屏幕上**可见**（截图像素，非 DOM 断言）
- [ ] 遮罩覆盖整屏（含状态栏下方区域）
- [ ] 屏幕边缘手势未抢走开关点击
- [ ] 点击后无系统 UI（状态栏/导航栏/输入法）干扰

> **能力已确认**：无障碍 `accessibilityConnected: true`；
> `phone_control` 的 action 实测含 `tap`/`click`/`swipe`/`screenshot`/`long_press`/`input`/`scroll`/`back`/`launch`/`read`。
> **注意**：Shizuku 通道（socket）的命令集是 `logs/session/status/stop/termux_*`，
> **不含触控** —— 触控走的是**另一条通道**（Android 无障碍服务），两者独立。

### 5.4 ⚠️ 主题机制：**一处已订正的错误结论**（重要）

> **我曾在本文档写过「上游 Web 层完全没有深色支持」—— 那是错的。**
> 错因：只在 CSS 文件里搜 `prefers-color-scheme`（得 0 处）就下了结论，
> 而**上游的深色机制是属性选择器，不是媒体查询**，且变量由 JS **内联写在 `body` 上**。

**上游深色机制的真实形态**（读 `dsh-client-ui-layout` 的 `theme-presenter.d.ts`）：

```
· html { color-scheme }        → 原生 UA chrome（滚动条、表单控件）
· body[data-ds-dark-theme]     → 深色基础调色板（token stylesheet 的属性选择器）
· 主题的 alias-token 覆盖       → 以内联 CSS 变量写在 body 上
· html[data-ds-theme-source]   → light / dark / system
· meta[name="theme-color"]     → 周围浏览器 UI
```

**实测证据**（设备真实引擎，给 body 加 `data-ds-dark-theme` 前后）：

| 变量 | 浅色 | 深色 |
|---|---|---|
| `--dsw-alias-bg-base` | `#fff` | **`#151517`** |
| `--dsw-alias-label-primary` | `#0f1115` | **`#f9fafb`** |
| `--dsw-alias-border-l1` | `#0000000a` | **`#ffffff0f`** |
| `body` 背景 / 文字 | `rgb(255,255,255)` / `rgb(15,17,21)` | `rgb(21,21,23)` / `rgb(249,250,251)` |

⇒ **上游深色支持完整**；本层 CSS 用 `var(--dsw-alias-*, 兜底)` 模式 ⇒ **自动跟随**。

**本层深色验收：13/13 通过**（`verify-dark-mode.mjs`）——两态下形态层激活、
开关/遮罩接管、可点区达标、文本可见、且**几何完全一致**（主题不改布局）。

**唯一发现的真实瑕疵（已记录，未擅自改）**：

```
⚠ --dsw-alias-border-default：上游**未定义** ⇒ 永远用兜底 #ddd
   用在本层 L50 / L75 两处「底部边框」
   上游的 border 变量命名是 -l1/-l2/-l3/-l4，**没有 -default**
   变量名是从 jet-hub 层沿用来的（jet-hub 自己也用错）
   后果：深色下 #ddd 相对 #151517 是**亮色线条**
```

**为什么不当场改**：改成 `-l1` 会让**浅色下**的边框从 `#ddd`（可见灰线）变成
`#0000000a`（几乎透明）⇒ 改变原设计意图，属产品判断，**交用户定夺**。

### 5.5 token 接入的作用域（这条**结论正确**，保留）

⇒ token 让**原生壳面**跟随系统深色（经 `values-night/`）；

## 8. 本会话抓到的工具缺陷（**读这节能省很多时间**）

共同点：**验证手段本身不可信** —— 比被测对象有缺陷更危险，因为它们会把结论**反向报告**。

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | APK 自动发现未校验进程身份 | 读到**别的 App**（多闪）的 APK，判定对象错 |
| 2 | `--realapp` 未清注入污染 | 验的是注入产物 ⇒ **假绿**（曾得 23/23 全绿，实际未修） |
| 3 | 版本判定只看 JS | 「部分落后」被报成「已装最新」⇒ 验收背书了旧版本 |
| 4 | 断言 `box` 与 `box` 自比 | 恒真 ⇒ **假绿**（"开关位于 header 内"一直是绿的但没验任何东西） |
| 5 | `slot-register-audit` 偶发退出挂起 | CI 可能随机变红（已加超时重试，**不掩盖**）。**已深度定位**：见下方专项说明 |
| 6 | 预演未清"第二条注入路径" | 页面里两份形态层并存 ⇒ 预演的不是新包行为 |
| 7 | 语义指纹查错载体 | **误报**（CSS 注释冒充组件内容）或**漏报**（组件内容去 JS 里找） |
| 8 | 文档/注释里的错误依据 | 代码对但依据错 ⇒ 后人照依据改会把对的改成错的 |
| 9 | 审计脚本**偶发假红**（报 24/35，重跑 6 次全 35/35） | 让正常的东西被怀疑 ⇒ 浪费排查、可能误改正常代码。**已加异常重试 + 失败项明细**，并做**双向自证**（重试不得盖掉真缺陷） |

> **注意方向**：缺陷 1–8 是**假绿**（把坏的报成好的），缺陷 9 是**假红**（把好的报成坏的）。
> 两者同级危险，共同点是「**验证手段本身不可信**」。
> 修「重试」这类逻辑时**必须双向自证** —— 只测"重试成功"会落入「自证永远绿」的陷阱。

**教训**：
- 说"已验证"前必须**真跑过**，给出命令与结果；
- **状态推进后要回头清理旧结论**（本会话修正了多处"仍未做"的过时标注）；
- **先找最简单的确定性证据**，再考虑复杂解析（例：判断"设备包是否含某改动"，
  用**时间线**（安装 08:01 vs 合并 09:23）比解析 `resources.arsc` + dex 常量池简单且无歧义）；
- **核实代码存在性用 `read` 而非 `grep` 中文**（`grep` 匹配中文关键词会因编码/全角差异漏匹配，
  本会话曾因此误判"重试机制不见了"）。

### 专项：`slot-register-audit` 偶发退出挂起（**已定位，勿重复调查**）

| 项 | 结论 |
|---|---|
| 现象 | 输出**已完整打印** `结果：6 passed / 0 failed`，但进程不退出（`exit=124` 超时） |
| 频率 | 静默 **16%**（4/25）；4 个后台 CPU 进程时 **40%**（10/25）⇒ **负载敏感** |
| 现场 | `/proc/<pid>/`：`State: S`、`Threads: 3`、`wchan: futex_wait_queue_me`；三个线程（`node-MainThread` / `node-V8Worker` / `SignalInspector`）**全部卡 futex** |
| 判定 | **Node 26 在 Android（bionic libc）上的退出竞态**，**非本层逻辑缺陷** |
| 已排除 | `process.exit` 本身 / import 模块 / mkdtemp+rmSync / 遍历真实引擎树 / 运行时长 / 其它 3 个测试均 0 挂起 |
| 缓解 | 保留 `ci-compat.test.mjs` 的**超时重试一次**（第 71–98 行），输出标明「首次超时已重试」，**不掩盖** |
| **不要做** | 试过 `setImmediate(() => process.exit())` 等改法：25 次样本看似更优（7→1），但 **50 次样本推翻**（A=3, C=3）；交替测量差距在噪声内 ⇒ **无证据支持改动，保持现状** |

## 10. 术语表

| 术语 | 含义 |
|---|---|
| **胶囊 / capsule** | `.github/capsule/`，全部自有代码的源材料，构建时外挂 |
| **形态层** | `dsh-phone.js` + `.css`，把桌面壳改成手机形态（断点 767） |
| **标记层** | 形态层发布到 `<html>` 上的 `data-dsh-*` 事实（如 `data-dsh-mobile-form`） |
| **接管式** | 组件挂载时发布 `data-dsh-*-mounted` 事实，CSS 消费它；组件没渲染则保留旧行为（**安全双向**） |
| **槽位 / slot** | 上游提供的扩展点（`ctx.slots.inject` / `register`） |
| **combo 请求** | 引擎把多个插件合成一个 URL（11 个模块，约 1.53 MB） |
| **三层验收** | 代码层 + CDP 层 + ADB 真人操作层，缺一层即未验收 |
| **预演 / `--preview`** | 把**即将发布**的产物投入运行中的引擎验收，回答"新包能不能过" |
| **代次判定** | `current` / `older-capsule` / `stale` / `baseline` / `other`，描述设备装的是哪一代 |
